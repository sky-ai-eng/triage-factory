# CLAUDE.md

This file provides guidance to Claude Code when working with code in this repository. This is a public repository. Under no circumstances should you commit sensitive information or custom configuration files related to specific deployments to git.

## Build, lint, test

```bash
# Full build — frontend first (Go embeds frontend/dist/), then the binary.
# Frontend uses pnpm (pinned via the "packageManager" field; `corepack enable`
# provisions it). The agentproc SDK runtime installer still uses npm by design.
cd frontend && pnpm install && pnpm run build && cd ..
go build -o ./triagefactory .

# Run (default :3000, opens browser)
./triagefactory [--port N] [--no-browser]

# Lint + format (Go + Rust harness + frontend) — same gates CI runs
./scripts/lint.sh           # check only
./scripts/lint.sh --fix     # auto-fix

# Go tests
go test ./...
go test ./internal/routing -run TestRouter_Dedup

# Frontend dev server (proxies /api to backend)
cd frontend && pnpm run dev

# Nuke local DB + config + keychain entries (fresh first-run flow)
./scripts/clean-slate.sh

# Multi-mode (Postgres + GoTrue + SeaweedFS), on demand only — not part of
# the default flow above and never run automatically:
./scripts/multi-mode-dev.sh up            # start deps via docker-compose.yml + migrate
./scripts/multi-mode-dev.sh run           # run the host binary as the CONTROL half (API on :3000)
./scripts/multi-mode-dev.sh run executor  # run the EXECUTOR half (separate terminal; needs runsc + caps)
./scripts/multi-mode-dev.sh down          # tear down
```

The repo-root `.claude/settings.json` registers a `PostToolUse` hook that runs `goimports -w` on edited `.go` files and `prettier --write` on frontend sources — do not duplicate that work manually. In practice this means you can write/edit Go code that references a new package without hand-adding the import line first; goimports fills it in after the edit lands. Caveat: the hook runs after *every* Edit/Write call, so it strips an import as unused if you add it in one call and only add the code that uses it in a later call — add an import and its first use in the same Edit/Write call (or just skip writing the import yourself and let goimports add it once the using code is in place).

## Architecture

Triage Factory is a **single Go binary** (HTTP server + pollers + delegated-agent spawner) with a **React SPA embedded via `go:embed`** (see `embed.go`). State lives entirely on the user's machine: SQLite at `~/.triagefactory/triagefactory.db` (user settings persist in the `settings` row — `internal/config` reads/writes via `config.Init(db)` at startup), credentials in the OS keychain (`internal/auth`).

### The binary has three boot identities

`main.go`'s `run()` resolves a **boot identity** first thing (`bootident.go`) and branches everything on it — the same discipline as `TF_MODE` / `TF_ROLE`: a resolved parameter, never a late ambient read. The inputs are argv (what the caller wants) and the sandbox marker `TRIAGE_FACTORY_SANDBOXED` (where the process is):

- **server** (no CLI args) — HTTP API + websocket hub + pollers + scorer + event router + delegation spawner.
- **host-cli** (CLI args, no marker) — operator subcommands (`install`, `migrate`, …) plus the local-mode agent verbs. Owns local state: mode/role resolution, deployment secrets, the SQLite DB (opened eagerly, migrated per invocation). `cmd/exec/` provides scoped GitHub/Jira subcommands the agent uses instead of calling those APIs directly, so credentials stay in the keychain and activity is auditable via `conversations` / `artifacts`.
- **jail-cli** (CLI args + marker) — the same `exec` verbs invoked _by a delegated agent inside its sandbox_, as a **pure RPC client**: no `runmode`/`TF_ROLE`/`secretenv` init, no `db.Stores` (structurally — `exec.HandleSandboxed` is handed a client and never the means to build one), and the agenthost client dialed against `/run/tf.sock` at boot, failing closed there if the socket is absent. Everything a verb touches, state and credentials alike, resolves daemon-side. Only exec verbs, `status`, and help dispatch here; every other subcommand is refused by name, because opening a DB under the jail's `HOME` would write junk state into the agent's own worktree.

### Core data model

The core data model is four levels, each with its own lifecycle:

```
Entity (PR #18 / Jira SKY-123)     ← long-lived, from first poll until closed/merged
  ↓
Events                              ← append-only; every poller detection + system emission
  ↓  (0 or 1 — only if a task_rule or prompt_trigger predicate matches)
Task                                ← "this entity needs attention, because of this event type"
  ↓
Conversations                       ← durable agent context: one row per transcript, any surface
  ↓
Claims                              ← one row per executor engagement with a conversation
```

**Conversations · messages · claims** is the unified agent data model (it replaced
the former `runs` fusion table): a *conversation* is the
durable context — type (`delegation` | `interactive` reserved |
namespaced `subagent:<kind>` reserved), task/trigger linkage, work-lifecycle
status (stored vocabulary `queued|running|open|terminals` — spend and KV-cache
warmth are derived from `messages`, never stored), `runtime` ratchet
(`sdk`|`native`), `sdk_session_id`, archive timestamp. A *claim* is one executor
engagement (executor id + boot epoch, sealed-credential pubkey, `phase` — the
live engagement's setup/parked sub-state, `fetching|cloning|agent_starting|
awaiting_credentials`, coalesced over the conversation's stored status on display
reads so a retry never rewrites the conversation row — at most one active per
conversation, schema-enforced). The transcript itself is the
`messages` table: one row per neutral API message, `delivered=false` rows are the
universal pending-input queue (follow-ups, staged injections — the former two
side-tables), `window_state`/`seq` are the native
loop's assembly columns, and `user_id`/`claim_id` attribute each row to the
requesting user and producing engagement. Queue-is-truth generalizes: "needs
driving" = a queued conversation or one with undelivered input and no active
claim.

Key invariants:

- **Entities are durable, events are immutable, tasks are ephemeral, conversations are the work.** Memory is written per-conversation but materialized per-entity via `entity_links`.
- **Dedup:** at most one active task per `(entity_id, event_type, dedup_key)` — enforced by a partial unique index in `tasks`. `dedup_key` is usually empty; open-set discriminators (label name, status name) use it to get separate tasks per value.
- **No retroactive task creation.** A new task_rule or trigger applies to events _going forward_. Historical events in the log are not re-evaluated.
- **Tracking changes are forward-only — the mirror of the rule above.** Adding a repo/project to a team's tracked set doesn't retroactively mint tasks for its history; removing one doesn't retroactively prune or close existing tasks. The team↔repo gate (`internal/routing` `handlerScopeMatchesEvent` + `TracksRepoSystem`) filters _future_ matches only; it deliberately does **not** reconcile `task_teams` visibility for tasks already created while the repo was tracked. A task is durable work (may have an in-flight run, an open PR, agent memory), so untracking never silently destroys it. This is symmetric in multi-team (team A untracks a shared repo → A keeps tasks it already had, gets no new ones; B is unaffected) and correct in solo N=1 (one team, so pruning visibility would orphan the task to nobody). Tradeoff acknowledged: an untracked repo stops polling, so its open PRs never emit the close event that would retire stale tasks — the answer is an explicit user-initiated "dismiss" affordance (its own ticket), never an automatic purge wired into a config save.
- **Events split on discriminators that change whether the situation needs attention** (`ci_check_failed` ≠ `ci_check_passed`, `review_approved` ≠ `review_changes_requested`). Attributes that just narrow the same situation (reviewer, check name, repo, label) stay as predicate-filterable metadata. Don't proliferate event types for Cartesian products.
- **Entities are org-wide; the team relationship is derived, not stored.** Repos/projects are configured per-org, so polling produces one shared entity per real object (`org_id`, no `team_id`) — forking per team would break the snapshot-diff re-emit invariant and the append-only log. **Standing rule (multi-mode read scoping):** every new entity-backed read must do one of — (i) join through team-scoped `tasks` (tasked-reads; e.g. `Tasks.ListActiveRefsForEntities`), (ii) be gated by the team's **tracked set** (GitHub repos / Jira projects attached to the viewer's teams, via the `team_github_repos` / `jira_project_status_rules` RLS semi-joins), (iii) filter by the requesting user's identity (personal views like the dashboard), or (iv) be explicitly annotated org-wide for a system job (e.g. `EntityStore.ListActiveTerminalCandidatesSystem` for the routing package's terminal-state reconciliation sweep). A default `org_id`-only entity list is a cross-team leak once polling is org-wide. Two reads use the tracked-set semi-join because they surface *untasked* entities the task semi-join can't reach: the Jira stock/discovery deck (`ListActiveJiraTeamScoped`) and the **factory belt** (`FactoryReadStore`, `internal/db/postgres/factory.go` — TFAC-516 moved it off the prior task-existence semi-join so belt density stops being a side effect of task creation). Postgres-only; SQLite/local is N=1 and stays unscoped. **Standing rule (multi-mode write scoping):** membership is the read gate, never the write gate. Mutating an org-wide entity — one with no `team_id` to write against, so the change lands on every team tracking it — requires an **admin**: org admin, or team admin of a team whose tracked set contains it (`TracksRepoViewerAdminScoped` is the pattern; `repoMutationAccess` in `internal/server/repos_handler.go` is the reference handler). RLS cannot express this — `repositories_all` is `org_id`-scoped by construction — so the handler predicate is the *only* enforcement and there is no DB backstop to catch a mistake. Split the two gates explicitly rather than reusing the read predicate. Denials are two-valued and both matter: outside the caller's tracked set → 404 (it isn't in their list either, disclose nothing); inside it but not an admin → 403 (a 404 for a row they can see reads as a bug).

### Event bus is the central pub/sub

`internal/eventbus` — `main.go` wires subscribers:

- `ws-broadcast` forwards every event to the frontend via websocket.
- `scorer` reacts to `system:poll:*` sentinels and kicks the per-org `ai.Manager.Trigger(orgID)`.
- `profiler` reacts to `system:poll:*` GitHub completions and kicks the per-org `repoprofile.Manager.Trigger(orgID)` — a TTL-gated repo-profiling pass. This is what profiles new / stale / newly-reachable (App-only) repos with no "github changed" plumbing, in both run modes. The explicit "Re-profile" button (and a tracked-repo-set change) calls `Trigger(orgID, force=true)` to bypass the TTL.
- `router` (`internal/routing/router.go`) consumes `github:*` / `jira:*` events, records them, creates/bumps tasks per task_rules, and fires matching prompt_triggers (auto-delegation). Also owns inline close checks and `ReDeriveAfterScoring` (post-scoring trigger pass for deferred `min_autonomy_suitability` thresholds).
- `poll-tracker` records poll completions into the durable, org-scoped `poll_readiness` table (both dialects) that gates `/api/jira/stock` and drives the one-shot "config took effect" toast (announce-pending, cleared after one completion). Because it is durable — not the former in-memory flag — the gate reflects the last synced state across a process restart; it is re-armed by a config change (`MarkRestarted`), not by boot.

Pollers publish events to the bus rather than invoking callbacks directly. This is how a poll cycle, a scorer run, and a UI push all stay decoupled.

### Poller / tracker

`internal/poller` manages GitHub + Jira pollers. `internal/tracker` does the diff logic: snapshot → refresh → diff against prior snapshot → emit typed events only on transitions. The snapshot-diff is the _sole_ source of truth for re-emit prevention — a check-run ID seen last cycle doesn't fire again. See `docs/concepts/tracked-events.md` for the taxonomy.

### Delegation (the "Agent" column)

`internal/delegate/spawner.go` + `internal/worktree` — delegation spins up a **headless Claude Code instance inside an isolated git worktree**. Credentials are hot-swapped into the spawner on config change (see `SetOnGitHubChanged` in `main.go`); the spawner instance itself is created once at startup. Agents stream stdout into `messages`; structured outputs (PRs opened, reviews posted) land in `artifacts` — one row per external object, uniquely keyed `(org_id, dedup_key)` so the same object captured twice (once via an exec verb, again via reconciliation) upserts instead of duplicating, with `provider` + `kind` discriminating the shape and a nullable conversation link (`ON DELETE SET NULL`) so the row outlives a purge of the run that produced it. Orphaned worktrees from crashed runs are cleaned on startup via `worktree.Cleanup()`.

A PR run's static `<task_context>` carries a **history skeleton** (`internal/prskeleton`) alongside the point-in-time event fields: the PR's commits, reviews, and lifecycle transitions, collapsed to a line budget in three tiers (full → runs folded to counts → landmarks retained with the gaps elided). It is fetched per run/step from two REST GETs — the PR object and `issues/{n}/timeline` — so the only capability required is `Get(ctx, path)` and it inherits whatever credential path the run already resolved. Best-effort: a fetch failure logs and yields an empty block, never a failed run. It renders **inside** the task context's untrusted-marker region, since commit subjects and PR titles are externally authored.

### Team knowledge

One knowledge base per team, and **the storage prefix is the visibility** — there is no ACL, no visibility column, and no per-folder row (a `team_kb_folders` table was rejected as a second source of truth every listing would have to join). `internal/kbstore` is the only place a KB address is built, over two closed-vocabulary roots — an object key in multi, `<orgID>/teams/<teamID>/kb/private/…`, and the same shape minus the org segment on disk in local (`OrgRoot` collapses at N=1): `private/` is readable through its own team's gate, `shared/` by any member of the org. **Publishing is a move between the roots**, which is also rename and reorganize — one verb (`POST /api/teams/{team_id}/kb/move`) rather than four spellings of a path change, and it refuses on a collision so a folder publish lands whole or not at all. The layout under a root is a hierarchical folder tree with per-segment validation (non-empty, no traversal, no separator inside a segment, no dot files, capped depth and length) enforced at the single door every write passes. Two backends behind one `kbstore.KB`: multi rides the shared `internal/storage` object seam so every pod is equal, local writes plain files at `<OrgRoot>/teams/<teamID>/kb/{private,shared}` and constructs no blob store at all. The HTTP surface is team-scoped and addressed at the team that OWNS the knowledge — an org member browsing another team's published notes calls the same routes on THAT team id, and the roots they may read narrow to `shared` alone; a `private/` path is 404-invisible to them rather than 403, while writes are 403 for a non-member because the team itself is org-visible. Nothing ever writes another team's KB.

**Every delegated run is staged with knowledge, and the resolution is a foreign key, not an inference**: `task.team_id` alone decides it — no model in the path, nothing to wait on, no cross-pod call. At claim the run tree gains its task team's whole KB (both roots, root names preserved) under `_tfac/knowledge/team/…` plus every other active team's `shared/` root under `_tfac/knowledge/org/<team-slug>/…`, copied in like the prior-memory materializer beside it and advisory in the same way (a store failure logs and skips; a run without knowledge still works). A rendered **manifest** — the folder tree with each document's first line — rides `<run_context>`, and only when something was actually staged: it is per-run data, so it can never live in an `agentprompt` block, whose text has to stay byte-identical across runs to remain a cacheable prefix. The blocks (`verbs/team-knowledge{,-native}.txt`, one per runtime) say the tree exists and what its two levels mean; the manifest says what is in it today. Runs read, humans write — the staged copy is rebuilt from the store on every launch, so it is excluded from a parked run's workspace snapshot (`scratchExcludes`) and anything an agent leaves there is discarded. A warm blueprint step keeps the first step's copy: the tree belongs to the sandbox identity by then, so nothing is re-staged and no manifest is composed for it.

### Sandbox, isolation, and executor credentials (multi-mode)

Which engine drives a conversation is the `conversations.runtime` ratchet (`sdk` | `native`), stamped at mint and never changed. **The enqueue stamps it per dialect, and the dialect IS the mode** (`conversation_queue.go`, both sides): Postgres mints delegations `native`, SQLite mints them `sdk`. So a multi delegation runs on the in-process Go agent loop (`internal/agentloop`, calling the provider through `internal/inference` from this process) and a local one runs on the SDK. Both arms stamp explicitly rather than leaning on the column DEFAULT, which is what makes the SDK engine *unreachable* for a multi delegation — the ratchet means nothing ever switches, so an engine no mint writes is an engine nothing runs.

An SDK conversation executes through `internal/agentproc.Run`, which spawns the Claude Code SDK as a `node` subprocess, and is **local-only**: `Run`/`RunInteractive` refuse to spawn in multi mode (`errSDKLoopInMultiMode`), where every conversation runs `native` and nothing spawns node. Local takes the direct spawn. A `native` conversation jails only its *tools*: the loop itself runs in the executor process, so its cell is built with **no model channel at all** — the sandbox env never carries LLM-proxy coordinates — and `shouldSandbox()` (= multi && Linux) gates exactly one thing, the resident tool-host jail (`agentproc.LaunchToolHost`); everything below about capabilities and isolation is that cell's, multi-mode only. (The system jobs — scorer/profiler — bypass all of this in multi mode: `internal/systemllm` makes direct, toolless LLM calls with no subprocess and no sandbox; local mode still runs them through the SDK subprocess.)

That direct spawn is not bare, though: on Linux a **local delegated run** is wrapped in a bubblewrap mount namespace, default-on (`internal/agentproc/localsandbox`, gated by `TF_LOCAL_SANDBOX` via `runmode.LocalSandboxEnabled()`; `RunOptions.LocalSandbox` nil = the pre-sandbox spawn, byte-identical). It is **courtesy isolation, not a boundary** — same uid, shared network, shared `/proc`, the framing `internal/pushpolicy` uses — so nothing in the multi-mode posture below rests on it, and it keeps an escape hatch a real boundary would not. The plan is whole-host-ro, then mask-and-bind-back: tmpfs over the operator's home, the state root, the temp dir and `/run`, with only the run's own tree, its gh-channel dir, TF's hooks/gh/SDK, `~/.claude`, the host's resolver files (`localsandbox.DNSPaths` — `/etc/resolv.conf` is a symlink into `/run` on systemd-resolved hosts, so the mask breaks DNS without them), and the run's `--add-dir` grants bound back. Three things follow from it and are wired for it: the run's exec verbs go over an agenthost socket under `<StateRoot>/agenthost` (`agenthost.StartLocal`) with `TRIAGE_FACTORY_SANDBOXED=1` flipping the CLI to its jail-cli identity, its worktree is materialized as a self-contained clone (`worktree.selfContainedRunTrees`, the same reason multi's is), and an org with no configured git identity commits under `githooks.FallbackIdentityConfigPairs` since the operator's `~/.gitconfig` is masked. Boot probes bubblewrap and **refuses to start** if it can't build a namespace (`internal/app/local_sandbox_guard.go`) — never a silent downgrade; the probe builds the load-bearing part of the plan (the `/run` mask and those bind-backs) rather than only creating a namespace, since a plan that is uninhabitable boots green and dies at the first completion. The toolless system jobs pass nil today; macOS is a separate phase.

A delegated run combines three dangerous things in one place. It needs *machine powers* — creating network interfaces, firewall rules, changing file ownership — to build an isolated cell for the agent. It needs *real secrets* — a GitHub token, an LLM API key. And it is *exposed to hostile text*, because the agent reads PR descriptions and issue comments that anyone on the internet may have written.

Any one of those alone is fine. The danger is one process holding all three, because then a single bug — a parsing mistake on a PR body, say — hands an attacker both the secrets and the machine. So the executor is split into four processes. The invariant is that **machine powers are never combined with anything else**; secrets and hostile input *are* deliberately combined, in the per-run sidecar, because a credential-injecting proxy has to parse the traffic it injects into — which is why that process gets a per-run uid, no capabilities, and no database handle.

#### The four processes

**The cap-broker** (`cmd/capbroker`, `internal/sandbox`) has the machine powers and nothing else — it is the only holder of `CAP_SYS_ADMIN`/`CAP_NET_ADMIN`. Its entire job is building and destroying the **cell** — the word this codebase uses for one run's isolated environment taken as a unit: the private network (netns/veth/iptables), the memory limits (cgroup), the filesystem (the OCI spec from a fixed template), the per-run files under the socket root, and the jail process itself (`runsc`). Comments in `internal/sandbox` and `cmd/capbroker` use it that way throughout ("another cell's uid", "a live cell", "cell teardown"), and it is deliberately a wider word than *jail*, which names only the `runsc` process at the centre of it. It holds no secrets and never reads a single byte the agent produced. It takes orders over a tiny host-only unix socket, and it checks every order hard (`ValidateLaunchParams`, `validateRunTreeRoot`) — if the orchestrator asks it to change ownership of `/etc`, it refuses, because the target isn't a run tree it already owns.

**The orchestrator** is the main Triage Factory server — the API, the dispatcher, the database. It has **zero** machine powers; they are dropped at exec via `setpriv` (Go can't drop reliably in-process) and cannot be picked back up. It holds no per-run agent credentials, and it does not parse the agent's output. It is the process with the broadest *data* access and the narrowest *power*.

**The credential sidecar** (`cmd/runsidecar`) is one process per running agent, and it holds exactly one run's secrets. No machine powers, and **no database handle** — it reaches persistence only through narrow, validated relay calls the orchestrator answers (`cmd/exec/agenthost/relayserver.go`). It runs the little proxies the agent's traffic flows through (LLM, git, egress, the fetch relays, the `gh` credential injector) plus the agenthost socket the agent's `tfac exec` verbs dial. Egress specifically has three lanes — CONNECT tunnel (`internal/egressproxy`), fetch relay (`internal/egressrelay`), credential proxies — with a probe-first procedure for adding ecosystem support; see `docs/security/sandbox-egress.md` and the CLAUDE.md in each lane's package before touching any of them. Its per-run uid (the `SidecarUID` band, `20000+`) is the isolation boundary between concurrent runs' credentials.

**The sandbox** is the gVisor jail where the agent actually runs. It holds nothing: no powers, no real credentials, just placeholder tokens pointing at its own sidecar (**Property B** — no real credential ever enters the jail's env, argv, or any file; the real one is attached on the upstream hop). It is the one thing deliberately exposed to hostile input, because reading PR bodies is its job. Per-run fail-closed egress allowlist.

#### What that looks like in motion

When the agent runs `gh pr view 7`, its environment points `gh` at an address on its own private network with a fake token. That address is its sidecar. Real `gh` talks to it believing it is a GitHub Enterprise server. The sidecar strips the fake token, attaches the real one, forwards the request to GitHub, and streams the answer back.

So: the agent never possessed the real token. The orchestrator never saw the agent's traffic. The broker built the network the traffic crossed but has no idea what flowed over it. Each process did its one job with only the one dangerous thing it needed.

**Executor credentials never come from the secret store.** On `TF_ROLE=executor` the secret store is disabled (`pgstore.NewWithoutSecrets`; `TF_SECRET_ENCRYPTION_KEY` is never loaded). Credentials arrive as **sealed per-claim bundles** — the control plane resolves and seals them (`internal/credprovision` → `internal/credseal`) to the active claim's published sidecar key, writes a `claim_credentials` row, and the executor unseals once at claim and threads the plaintext on ctx (`credbundle.FromContext`). So executor-side code (proxies, agenthost, git) reads credentials from the **bundle**, never `stores.Secrets` — resolving from the disabled store is a recurring bug class. Local mode uses the live secret store directly (no bundle); there is no fused multi role that does — `TF_ROLE=all` refuses to boot in multi (TFAC-637), sandboxed runs REQUIRE a prebuilt per-run network + credential sidecar (`agentproc.Run` errors without one), and the former in-process proxy / clone-token / agenthost-over-stores paths are deleted. Full posture: `docs/security/security-overview.md` + `docs/security/privilege-separation.md`.

### Event-source availability

`internal/eventsource` answers, per org, which event sources can produce events for it — `available` | `unconfigured` | `disabled` | `unlicensed` | `wip`, read through the member-gated `GET /api/orgs/{org_id}/sources`. It is **derived on every read**, and every CAPABILITY input to it is unstored: each of those off-switches already exists elsewhere (unbind the credential, disconnect the workspace, let the licence lapse, don't ship the source), and mirroring one into a flag would be one more that can disagree with it. Core declares github and jira (probed from one shared credential load) plus the sources TF has declared and not built; anything outside core registers its own probe (`eventsource.Register`) the way it registers routing hooks and its entitlement gate, so `ee/slack` answers for slack without core holding a Slack symbol. A registration may be **multi-only**, which local mode *omits* rather than reporting off — every `ee/slack` route 404s there, so a state would be a claim about setup or licensing nobody is being asked to make.

The one stored input is **policy, not capability**: `disabled`, an org admin's deliberate off switch, on `org_event_sources` (`db.OrgEventSourceStore`, both dialects, keyed `(org_id, kind)` — its own table because the source vocabulary is a runtime registry, so a column per source would be DDL in both dialects for every new one, and because `org_settings` is a whole-row write behind a `version` token this surgical single-column write would have to fight). It mirrors nothing: the only other way to turn a source off is to unbind its credential, which destroys the configuration rather than suspending it. It resolves in `resolver.state` rather than in any probe, so a registered source gets it for free. Precedence is least-fixable-first — `wip` > `unlicensed` > `disabled` > `unconfigured` > `available`; `disabled` outranks `unconfigured` because telling a reader to go bind a credential for a source an admin turned off sends them to do useless work. It is a fifth value of `state` rather than a second field beside it, because every consumer keys on `state == available` and a consumer that forgets a second field silently ignores the pause.

The same derivation decides **what an agent is told it can do**. A run's `<tools>` section is composed from the org's available sources, unioned with the source the run is about (plus GitHub, which every run keeps) — never from the trigger alone, which is how a run started by a GitHub event ended up unable to read the Jira ticket its own pull request referenced. The available set reaches the composition (`agentprompt.ToolsReferenceForSources`) through two doors, by where the answer can be computed: local mode resolves live (`eventsource.AvailableKinds` under synthetic claims), while a multi-mode run reads the **claim's stamped tools manifest** — `claim_credentials.include_tools`, cleartext source names the brain resolves via `eventsource.AvailableKindsSystem` and writes beside the sealed bundle on the same provisioning pass — because an executor structurally cannot answer (its secret store is disabled, and an event-triggered conversation has no user identity to open a claims transaction as). Registered sources join the system door through `Registration.SystemProbe`; one that declares none is simply absent from the system answer. Callers union rather than intersect and fall back to a superset when the resolve fails (an unstamped manifest reads as "fall back", an empty one as a real answer), because the block is *documentation*: the gate that actually stops a verb is the credential funnel it resolves through, and an advertised verb that refuses names its reason, while a missing one just makes the agent improvise. The composition is canonical (core first, then registered sources, deduplicated) so two runs with the same set produce the same bytes.

Availability is **org-level and not about demand**: what a team tracks (repos, Jira projects, channels) never enters it — a team tracking nothing must still see Jira as available or there is no way in to track something. Two consumers read it: the event-handler create routes refuse an `event_type` whose source the org cannot produce (422 `INVALID_FIELD`, distinct from the entitlement gate's 403 — a licence is a permission fault, an unconfigured or paused source is a reference the caller can fix), and the event-handler read shapes carry a derived `source_available`. A handler whose source went away is still listed and still counted, which deliberately diverges from the entitlement gate that *hides* an unlicensed handler: absent means never yours, explained means not yet.

The off switch is written through `PATCH /api/orgs/{org_id}/sources/{kind}` (**org admin** — a source is in no team's tracked set, so the org-wide-mutation rule reduces to plain org admin, and unbinding the credential already takes one; the read beside it stays member-gated). **Off means off**: the source is not polled, produces no events, mints no tasks, and resolves no credential for an agent — a switch that stopped only one of those would be a control an admin cannot read the effect of. What it does *not* do is destroy anything: the credential stays bound, and it is forward-only, so existing tasks, in-flight runs and authored handlers are untouched, exactly as untracking a repo is. That non-destruction is the whole reason it sits beside `DELETE …/jira/access/credential`, which achieves the same silence by throwing the credential away.

**Not every source has the switch.** `eventsource.Disableable` is the rule, and GitHub is `required`: repositories, pull requests, the git channel a delegated run pushes through and every artifact a run produces are GitHub, so an org with it off is an org where nothing works — the control would only ever be a way to break a deployment silently. Required is a builtin-only property and never a `Registration` option, because a source declared from outside core is by construction one the product runs without. The rule is carried in three places rather than one: `Disabled` short-circuits on it (so every gate inherits it, and a hand-written row — `kind` is FK-free by design — is inert rather than catastrophic), `resolver.state` skips the policy lookup (a required source never resolves to `disabled`, whatever a row says), and the PATCH refuses with **422 `INVALID_FIELD`**, not 404: the source is real and the `GET` beside it answers for it, so a 404 would send a caller hunting for a spelling mistake. The wire shape carries `disableable` so a client never offers a control the write refuses.

Three gates enforce it, and they read one predicate — `eventsource.Disabled` (`internal/eventsource/policy.go`), which reads the row directly rather than resolving a `State`, because the machinery needs to know whether an admin said stop, not whether the credential also happens to be missing today. **Every one of them fails closed**; the tie-break throughout is that a wrong refusal costs a retry while a wrong permission is unrecoverable. (1) `Router.HandleEvent` is the boundary for *events*: it drops after recording and before task creation (append-only log stays complete, only the ephemeral layer is suppressed), reading a per-org cache invalidated over the `tf_ctl` relay and floored by a short TTL because that relay is lossy. (2) The Jira poll cycle's skip is the boundary for *API load*, not an optimization — "a turned-off source makes zero API calls" is measurable from the other end, by an operator watching their own Jira Data Center, so an unreadable policy skips the cycle (span outcome `policy_unreadable`, distinct from `disabled`) rather than polling. The GitHub cycle has no such check, deliberately: with GitHub required the answer is a constant, and a check would read as a suppression that can happen. (3) `cmd/exec/agenthost` refuses at the verbs' shared choke points, which is what cuts a paused source's verbs for a run **already in flight**: the Jira credential funnel (`jiraSystemClient`, the single point every Jira verb resolves through) for `tfac exec jira`, and the extension dispatch (`callExtension`, beside its entitlement gate) for every registered provider namespace — the namespace is the source kind, so Slack's verbs inherit the cut and a namespace naming no disableable source passes structurally. That check crosses `Runtime.SourceDisabled` (a relay op, like `CheckEntitlement`) because in multi mode the agenthost daemon lives in the capless sidecar and the policy lives in a database it does not have; it is read per call rather than cached, since a cache is a window in which a turned-off source still answers. Nothing touches the sealed credential bundle or the sidecar's proxies: the Jira REST proxy's only client is the agenthost daemon, which is gated above, and the git / `gh` proxies serve GitHub, which cannot be turned off. Disabling also **clears `snapshot_json` for that source's active entities** (`EntityStore.ClearSnapshotsForSourceSystem`, bumping `poll_seq` so an in-flight cycle's CAS misses): the snapshot-diff is the sole re-emit guard, so without it the first cycle after re-enabling would diff a pause-old snapshot into a burst of transitions. Cleared, those rows take the tracker's existing quiet-seed path — the one a snapshot-less stub takes — which seeds and emits nothing, terminal states included, so `internal/tracker/diff.go` needs no suppress-emit mode.

### Instance registry (fleet membership)

`internal/instance` + the `instances` table (`db.InstanceStore`) — every TF process's persistent identity and heartbeat, the substrate the horizontal-scaling epic's later phases (reaper, placement, fleet dashboard) read. The id is a file: `internal/instance.EnsureIdentity` mints (or re-reads) `<TF_STATE_ROOT>/instance-id` under an exclusive flock held for the process lifetime, so a restart keeps the same id and two processes pointed at one state root fail fast instead of silently sharing an identity. `app.New` resolves it first thing at boot, registers it (`Instances.Register` — an atomic upsert that bumps `boot_epoch` on every restart), and hands the (id, boot_epoch) pair to the spawner via `Spawner.SetExecutorID`, replacing the old per-boot random uuid that stamped the claim's executor identity. `Spawner.RunInstanceHeartbeat` renews the row every ~4s with the live capacity/admission snapshot (host memory headroom, the dispatch memory gate, semaphore occupancy) — moving state that used to live only on the process onto a row other instances (and eventually the fleet dashboard) can read. Every process registers, not just executors (deployment-wide visibility — build versions, health, the eventual lease holder); the row's `role` column carries this process's resolved `TF_ROLE` (`all`/`control`/`executor` — TFAC-582), stamped by `app.registerInstance` from `runmode.Role()`.

### Background-brain leader lease

`internal/lease` + the `leases` table (Postgres-only — see below) — the leader election that gates the background brain (pollers/tracker, the durable event-queue drain worker + sweeper, and — as of TFAC-583 — brain-gated `ExtensionAPI.OnReady` workers) so exactly one control pod runs it at a time under `TF_ROLE=control`. `lease.Manager.Run` drives acquire/renew off a Postgres row (`holder_id`, a `term` fencing token bumped on every acquisition, `acquired_at`/`renewed_at`); a holder self-demotes on its **own monotonic clock** once `TF_LEASE_DEMOTE_SEC` (default 15s) elapses since its last successful renewal, strictly before the `TF_LEASE_TTL_SEC` (default 20s) a successor needs to see elapsed before it may acquire — so a demoted holder is provably stopped before a new one starts. `internal/app`'s `startBrain`/`stopBrain` (`brain.go`) are the actual start/stop unit both the lease callbacks and (at `TF_ROLE=all`/local, which never elects — zero lease I/O) a direct `Run()` call drive. Non-leader callers of a background Manager's `Trigger(orgID)` or the poller's `PollSoon(source, orgID)` — config-save handlers on a standby — relay over the `tf_ctl` Postgres NOTIFY/LISTEN channel (`internal/ctlbus`) to whichever pod holds the lease; the relay is lossy by design (a dropped message just costs one deferred `system:poll:*`-driven pass). `GET /readyz`'s poller-alive hard check is lease-conditional: the holder is byte-identical to the original (TFAC-573) contract, a standby hard-checks only `db`+`migrations` and reports `poller_github`/`poller_jira` as the literal string `"standby"` (never 503, so an LB keeps every standby in rotation), and a `lease` field (`{name, holder_id, is_holder, term}`) appears on every control pod's response — `TF_ROLE=all`/local never wire `SetLeaseStatus`, so the field is omitted there, keeping that contract frozen. The org-scoped `poll_readiness` table (`db.PollReadinessStore`, both dialects) replaced two former in-memory, leader-coupled flags — the `/api/jira/stock` readiness gate and the one-shot "config took effect" toast — so any control pod's API reflects state the actual leader produced.

### The background-jobs model

The two system jobs — scorer, repo profiler — run on one org-level setting, `org_settings.background_jobs_model`, a `internal/modelcatalog` key. One knob for both: they are the same kind of work (short, toolless, no transcript) bought from the same budget. The picker is the whole catalog — the delegation gates (tool support, a 64k window) are about running an agent and do not narrow this.

`systemllm.ModelForSettings` is the rule, `systemllm.NewModelFunc` the store-backed adapter for the job that holds no settings row (the profiler instead resolves from the read it already does for the clone protocol). It is resolved **once per cycle** and passed down to the batch seam, so a cycle spends on one model and `system_llm_runs` records it. Unset, not offered by this build, or served by a provider the org has not connected are all one answer — `ErrNoModel`, the cycle skips with a WARN naming the setting — because TF ships no fallback model and a substituted one would spend somebody's money on a model nobody chose.

The dialect column defaults carry the §7 mode asymmetry as data rather than a branch: SQLite (local) defaults to `claude-haiku-4-5-20251001`, so a first run and an upgraded install both arrive pre-filled; Postgres (multi) defaults to empty, so a fresh org is forced through the setup pick.

### AI scoring

`internal/ai/manager.go` + `internal/ai/runner.go` — a per-org `ai.Manager` owns lazy per-org `Runner`s, each with its own trigger channel and single-flight cycle gate, so a slow cycle on one tenant doesn't head-of-line-block scoring on others. `Manager.Trigger(orgID)` is idempotent during an active cycle (signals merge). Scoring does **not** block on repo profiling — there is no `ProfileGate`. Profiling (`internal/repoprofile`) is an independent `system:poll:` subscriber (a sibling per-org `repoprofile.Manager`, same shape as the scorer); the scorer uses whatever profile context exists and improves on the next cycle as profiles land (eventual consistency). Repo profiles have a 3-day TTL and regenerate per poll cycle (the `profiler` subscriber) or on an explicit re-profile (which forces past the TTL).

### Prompt ownership

Prompt text is organized by **what kind of artifact it is**, not by which package consumes it. Three kinds:

- **Agent framework prompts — `internal/agentprompt`, the only package that owns agent-facing text.** Who the agent is, what harness it is in, what it may do. `Build(Spec)` composes `blocks/` per a Go manifest (`manifest.go`) across four axes: **surface** (machinist) × **runtime** (sdk | native) × **family** (claude) × **mode** (local | multi). Five rules keep that from becoming a combinatorial tree, and they are load-bearing: (1) nothing outside this package embeds agent prompt text; (2) each block file varies on **at most one** axis — a GPT set later is `identity/machinist.gpt.txt` plus a manifest arm, not a new tree; (3) `Build` is **byte-identical for a fixed `Spec`**, across runs and processes — that's the cacheable-prefix property, so a block file is **literal**: what it says is what the model reads, and a fact that differs per run arrives instead in the prompt's own `<run_context>` / `<task_context>` / `<tools>` sections, which the blocks refer to by name; (4) `Mode` is a **parameter**, never a `runmode.Current()` read inside the package, so both variants are testable without env manipulation; (5) the manifest is Go, not a config format. Both modes mediate the managed Git path through a per-run proxy and enforce the same base-branch policy (`internal/pushpolicy`). The mode axis remains necessary because only multi puts that path inside a gVisor jail with a fail-closed egress allowlist; local's process-scoped routing is a safety and identity guarantee for ordinary behavior, not a security boundary against the unsandboxed process. Tests enforce all of it: determinism, mode divergence, literal blocks, and no orphaned block files.
- **Shipped content — `internal/promptseed`.** The seed rows a team gets in the `prompts` table. The `.txt` in the repo is a *seed*: after provision the row is the source of truth and the user may rewrite any of it in the UI. `promptseed.Prompts()` / `promptseed.Blueprints()` feed the bootstrap seeder and the boot-time drift sync; the sync walks *blueprints*, so a prompt with no wrapping blueprint is seeded once and then never drift-corrected — shipping a default nobody can see or change is how guidance goes stale, which is why every shipped prompt today gets wrapped. Seed bodies are **literal**, under the same rule as the blocks and for a sharper reason: a prompt row is user-editable, so a default that depended on something the UI never taught would be an example of a capability nobody could reproduce. A body names the run's pull request, its event fields, its run root, and its branch convention by reading the `<task_context>` / `<run_context>` sections it is composed alongside.
- **System job prompts — next to their consumer.** Toolless LLM calls TF makes for itself, closer to a SQL query than to agent instructions: `internal/ai/prompts/batch-prioritize*` (scoring), `internal/repoprofile/prompts/` (profiling). No agent, no envelope, no tools, never user-visible.

`internal/ai` exports no prompt string, and `internal/delegate` does not import it. `ee/slack` contributes its verb docs inward via `agentprompt.RegisterToolsReference` at init — that registry is the whole reason it exists, since the ee-import-boundary guard means core can never import ee. Note `internal/server/prompts/` is a Go package of prompt *API primitives*, not prompt text.

### HTTP server

`internal/server/server.go` — plain `net/http` + `http.ServeMux` using Go 1.22+ pattern-based routing (`"POST /api/tasks/{id}/swipe"`). Each handler group lives in its own file (`tasks.go`, `settings.go`, `triggers_handler.go`, ...). The SPA is served from `embed.FS`; unknown paths fall through to `index.html` for client-side routing.

### Frontend

React 19 + Vite + TypeScript + Tailwind v4. Router routes live in `frontend/src/main.tsx`. All API calls go to `/api/*`; a long-lived websocket at `/api/ws` streams events (frontend listens via `hooks/useWebSocket`). `AuthGate` blocks the app until setup is complete.

## Conventions to know before editing

- **Schema: goose-managed forward migrations, fresh installs only.** The consolidated baseline (`202605130001`) is a hard reset — pre-baseline DBs are refused at boot via the brick check in `internal/db/migrations.go`. Operators run `triagefactory uninstall` (or `./scripts/clean-slate.sh` if working from source) and reinstall. New migrations land as `internal/db/migrations-sqlite/NNNNNNNNNNNN_description.sql` (12-digit `YYYYMMDDNNNN` version) with `-- +goose Up` / `-- +goose Down` markers. Down blocks are `SELECT 'down not supported';` no-ops. The brick check (`assertFreshOrCurrent`) gates entry to `goose.Up`: empty DB → proceed; `goose_db_version` contains the baseline (202605130001) → proceed; anything else → `ErrPreV1110Install`. Postgres migrations live in `internal/db/migrations-postgres/`; `db.Migrate(db, dialect)` routes to the matching tree. Postgres tests use the `internal/db/pgtest` harness — testcontainer with two connections (AdminDB superuser, AppDB authenticator+tf_app) — and skip cleanly when Docker isn't available. See `docs/for-agents/specs/sky-247-d3-multi-tenant-postgres-schema.html`.
- **Stores are dual-dialect behind one interface.** All persistence goes through the `db.Stores` interfaces (`internal/db`), implemented by **both** SQLite (`internal/db/sqlite`) and Postgres (`internal/db/postgres`) — a new store method is the interface + both implementations + a case in the `internal/db/dbtest` conformance suite (which runs against both). Each pod opens two pools: an **admin pool** (RLS-bypassed) and an **app pool** (RLS). Request handlers use the app pool under a per-request RLS context; JWT-less background jobs (pollers, scorer, delegation) use the `...System` method variants on the admin pool, with `org_id` bound by argument rather than RLS. The read-scoping standing rule above governs *what* those org-wide reads may return.
- **A single-row write returns the row it persisted.** Every `Insert`/`Update`/`Upsert` that touches one row returns `(domain.X, error)` — or `(*domain.X, error)` where a miss is an answer rather than an error — sourced from `RETURNING` on the write statement itself, never a follow-up read, and projecting the *same* column list and scan function the point read uses so the write shape can't drift from the read shape. This is correctness, not convenience: our upserts deliberately don't persist what the caller passed (`repositories` COALESCEs `external_id` and preserves the user's `base_branch` and clone status; `artifacts` preserves-on-empty `target`/`external_id`/`url` and pins `conversation_id`/`team_id` to the creating run), so an input struct is *designed* to be wrong as a picture of the row — and a read-back to correct it can miss a row that moved. Miss semantics don't change: an id-keyed write that hits nothing maps `sql.ErrNoRows` → the store's `ErrNoSuchX`, which is also what replaces the old rows-affected probes. `ON CONFLICT DO NOTHING … RETURNING` returns **zero rows** on conflict, so those are not mechanically convertible — each needs its own decision, not a sweep. A caller may ignore the returned row; a caller must never re-read to learn what the write already returned. Acceptance is one `dbtest` assertion per converted method — `dbtest.AssertWriteReturnedStoredRow`, returned row == follow-up point read — which covers the RETURNING semantics and column-list drift at once. What it does *not* cover by default is RLS: the conformance suites wire both Postgres pools to the admin (BYPASSRLS) connection so behavior stays independent of the auth path, and on a BYPASSRLS connection a `RETURNING` clause hands back its row unconditionally. An upsert's conflict arm has to satisfy the SELECT policy for the row it returns — a policy admitting the write but not the read-back yields zero rows from a statement that updated one — and only a claims-carrying transaction tests that. `TestJiraAppsStore_Postgres_ReturnedRowConformance` is the wiring that does; converge an RLS-gated write the same way rather than assuming the admin-pool run proved it. `RepositoryStore` and `ArtifactStore` are the reference implementations; every store in `internal/db` holds the standard now. Exceptions (bulk/sync writes, deletes, fire-and-forget bookkeeping, credential surfaces, `ON CONFLICT DO NOTHING` upserts, and the rest) are documented at the method or interface that carries them, not enumerated here.
- **Events catalog** is a read-only system registry seeded from `domain.AllEventTypes()` via `db.SeedEventTypes`. New event types must be added there _and_ the events_catalog table will reject emissions of unregistered types (FK from `events.event_type`).
- **System triggers ship disabled.** They're reference examples — users opt in or replace them. See `internal/db/event_handlers_store.go` (`ShippedEventHandlers`).
- **In code, the object is a conversation; `run` is the verb.** The schema settled this vocabulary first (`conversations`, `conversation_worktrees`, `conversation_signals`, `conversation_permissions`), and the HTTP API and websocket followed (`/api/agent/conversations/{conversationID}`, `conversation_update`). Go and TypeScript identifiers now match: a `conversations` row is a `conversationID`, never a `runID`. Three things keep the word and are not drift. **The verb** — `runAgent`, `Manager.Run()`, `runConfig`, `runmode`, `runtime`, `runsc`: these name the act of executing, not the row. **A `blueprint_runs` row**, which really is a run of a blueprint: `blueprintRunID`, `br`, and `BlueprintStore`'s `GetRun` / `MarkRunStatus` / `ListRuns`. **External vocabulary** — GitHub's `check_run` and `workflow_run`, whose `RunID` is theirs, not ours. Because the bare word no longer names our row, a `Run` you meet in Go is one of those three by construction rather than by convention.
- **The product still says Run, deliberately.** `RunStation`, the `/runs/:id` route, `{{RUN_URL}}` (published into GitHub PR bodies, so those links must keep resolving), and the `max_concurrent_runs` / `active_runs` wire fields all keep it — "run" is the more legible word for someone who does not think in agent primitives, and moving it is a per-surface product call, not a mechanical follow-through of the code rename. Route *bindings* are code, though: the path is `/runs/:conversationID`, which renames the placeholder without touching the URL. The operator env vars are NOT part of this surface: they follow the schema's vocabulary (`TF_MAX_CONCURRENT_CLAIMS`, `TF_MAX_CLAIM_ATTEMPTS`, `TF_CLAIM_MEMORY_LIMIT_MB` — the unit each governs is one executor engagement, a claim — and `TF_CONVERSATION_SIGNAL_PURGE_AFTER`, which governs the `conversation_signals` table). Two data values also still say run and are load-bearing as stored strings: the spend row's `source='run'`, and `pending_firings.fired_run_id` — which is a `blueprint_runs` FK, so it is correctly named and must not be swept.
- **Name a helper for the row it reads, and a key for the role it plays.** A function named for a *step* that actually reads the step's conversation says so (`blueprintDecisionForStepConversation`, `GetRunForConversation`) — a `blueprint_steps` row carries no outcome, so a name that stops at "step" points at the wrong table. And a package that keys something by an id it takes no view on — the run-root path, a snapshot blob — names the parameter for its **role** (`rootKey`, `keyID`, `namespace`) with a doc saying which id its callers pass, because a delegated run's tree is keyed by the blueprint run id (so one blueprint's steps share it) while a conversation with no blueprint keys by its own, and both reach the same helper.
- **Go module path:** `github.com/sky-ai-eng/triage-factory`. The GitHub org is `sky-ai-eng`.
- **Go version:** `go.mod` says 1.26.1, README says 1.23+; keep the floor modern but don't bump without reason.
- **User integration credentials never touch disk.** Per-user tokens that the running TF binary uses (GitHub PAT, Jira PAT, etc.) live in the OS keychain via `internal/auth`. Token fields in Settings show "leave blank to keep current" when a token is stored. This rule covers credentials the TF process reads at request time — it does NOT apply to multi-mode deployment secrets (DB passwords, GoTrue signing material, etc.), which live in the operator's `.env` like any compose deployment.
- **JWT verification.** `internal/auth/verify` wraps `MicahParks/keyfunc/v3` + `golang-jwt/jwt/v5` to verify GoTrue-signed RS256 access tokens against a remote JWKS. The **server auth path** is multi-mode only — local-mode boots without a GoTrue dependency and the request-handler middleware never constructs a Verifier. The `triagefactory jwk-init --verify` CLI smoke helper does construct a Verifier regardless of mode (operator-facing debug tool); that path is separate from the server. `triagefactory jwk-init [--write-env F]` generates the RS256 keypair GoTrue signs with — operator runs it once during install. See `docs/self-hosting/install.md`.
- **Two credentials, one identity.** `withSession` (`internal/server/middleware.go`) resolves either an `sid` cookie or `Authorization: Bearer tf_…` (`internal/apitokens`) and seeds the SAME request context from both — claims, and the active org via `httpx.WithOrgID` — so no handler branches on which arrived. The Bearer branch is a **peer, never a fallback**: any `Authorization` header sends the request down it and it is decided there, 401 on every failure (bad scheme, no row, revoked, expired, past the org's max-age cap, outside the token's CIDR allowlist — all indistinguishable), with no second chance at the cookie. Multi-mode only; local's synthetic-identity branch returns before the header is read. A token differs from a session in exactly one way, and it is enforced in one place: its org is **sealed at mint**, so `httpx.TokenAuthFrom(ctx)` marks the request and the `authz` org gates 404 any org the token does not name (`tokenScopeAllows`). Two corollaries. A route whose subject is the **deployment** — the operator fleet console — no token can name at all, and refuses Bearer with 403 at its shared gate. And a route that needs a *session specifically* (moving the cursor: active-org switch, org create, invite accept) reads `SessionFrom(ctx)` and 401s without one; the org must come from `httpx.OrgIDFrom`, never off the session row, or the route silently stops answering for token callers.
- **Runtime mode flag.** `TF_MODE=local|multi` is read once at startup by `internal/runmode` (called from `main()` before the argv-dispatch switch). Default is `local`. Downstream packages branch on `runmode.Current()`: `internal/db` picks SQLite vs Postgres, `internal/paths` (forthcoming with SKY-248 D4b) resolves state-root paths, future auth + sandbox tickets gate multi-only behavior. `runmode.LocalDefaultOrgID` is the synthetic org-context value local-mode callers pass everywhere a real `orgID` is expected — and it is local-only: the sentinel identities (`LocalDefault*`) never reach a multi-mode request or credential path, which threads the real `(org, team, user)` ids from request claims or the resolved conversation instead.
- **Role flag.** `TF_ROLE=control|executor` is a **multi-mode-only input** naming which half of the split a process runs: `control` serves the API/WS and competes for the background-brain lease; `executor` runs the dispatcher + sandboxes and takes no inbound traffic. Multi requires it explicitly (unset, `all`, or a typo fails boot — every multi deployment is the control+executor split, so per-run credential isolation is structural, not a knob); **local mode ignores `TF_ROLE` entirely** — the single-process shape is gated on the mode, and `runmode.RoleAll` survives only as the internal name of local's resolved inventory (the everything-plan, the instance-registry stamp). Resolved via `internal/runmode`; the split is specified in `docs/for-agents/specs/horizontal-scaling/`.
- **Branch naming.** Use `aa/TFAC-<NNN>` (uppercase ticket ID, no trailing slug) for ticketed work — e.g., `aa/TFAC-327`, NOT `aa/tfac-327-foo` or `aa/TFAC-327-handler-sweep`. Linear holds the descriptive title; the branch name's job is just to point back to the ticket. For un-ticketed work, `aa/<short-kebab-slug>` is fine. `aa/` is the user's initials (Aidan Allchin); the `codex/...` prefix that exists in the repo comes from a different agent (OpenAI Codex) — don't copy it.
- **No ticket references in code comments — with exactly one exception.** Keep `TFAC-`/`SKY-` ids and issue numbers out of source comments; they belong in commit messages, PR bodies, and branch names. Comments explain **why**; they never restate what the code does or assert what other code does. The sole exception is the deferral marker below, and it is the only form in which a tracker id may appear in source.
- **Comments describe what ships in this commit — never the history of how it got there.** When you remove or change something, just change it. No "formerly", no "renamed from", no "this replaced X", no note that an alias or fallback once existed and was deleted: a comment narrating code the reader cannot see sends them hunting for something that does not exist, and the codebase must read as an accurate description of itself at exactly this commit. The story of a change is told once, in the commit message and PR body, at the moment it happens — not retold forever at the site of the change. The one look-backward that belongs in source is a constraint that still binds: "stored rows carry this value", "deployed clients send this name" is present-tense fact about live data, stated as the constraint it is rather than as a chronicle of the code that created it.
- **Deferred work is tracked in code or it does not exist.** Any work knowingly left undone — a case not handled, a shape not covered, a follow-up someone intends to do — is marked at the place it is missing, against whichever tracker holds it:

  ```go
  // TODO(TFAC-788): <what is missing, and what depends on it>
  // TODO(#412): <the same, when a GitHub issue is the tracker>
  ```

  **Either form is fine, and one is enough.** Which you use follows from where the work is actually tracked: the Linear project is contributor-only, so an outside contributor cannot file there and a GitHub issue is their tracker. Don't mint a second id in the other system just to carry both — a duplicate that nobody updates is worse than a single live reference.

  Two conditions, both required. The tracker must **already exist and already describe this specific gap** — pointing at something that doesn't mention it is how work gets lost twice, once in the code and once in the tracker. And the marker goes at the site of the gap, not in a summary somewhere: "I'll note it in the PR description" is not tracking, because PR bodies are not read again after merge.

  The alternative to a marker is doing the work now. Choosing to defer is fine; leaving the deferral untracked is not, and neither is inventing an id to satisfy the format. If nothing covers it, file it first or say so and let the user decide — a `TODO` pointing somewhere that does not describe the gap is worse than no `TODO` at all, because it looks tracked.

## API design

Rules for every `/api/*` route, existing or new. The backend cleanup spec (`docs/for-agents/specs/backend-api-cleanup/`) holds the full audit of where the current surface deviates and the remediation order — when you touch a handler listed there, converge it; never add a new deviation. The frontend follows the same contract from the other side: one shared error parser and one pagination hook in the API client, no per-call ad-hoc parsing.

- **One intent per route.** A route does one nameable thing with a fixed body schema. No discriminator field that changes which other fields are meaningful (`action`, `kind`, `auth_method` switching arms), no field whose *emptiness* selects a second behavior (blank-means-delete, blank-means-keep). If two operations need different required fields, validation, or response shapes, they are two routes. Verb routes (`POST /…/{id}/approve`) are only for effects a field write can't express — external API calls, multi-row atomic transitions, process control.
- **Bad calls fail.** Strict body decoding — unknown fields are rejected. Invalid values are rejected with the field named — never clamped, defaulted, case-folded, or silently dropped. Query params parse strictly: a malformed filter is rejected, and must never *widen* a result set by falling back. Never report success for work that didn't happen.
- **Uniform reads.** Every resource: `GET /…/<resource>/{id}`, `GET /…/<resource>/by-name/{name}` where a unique name exists, and `POST /…/<resource>/list` taking `page_size`/`page_token` and returning `{items, next_page_token, total_count}`. No bare-array lists, no unbounded fetch-the-world queries, no hardcoded store LIMITs that truncate silently. Store-layer pagination work is the accepted cost. Reads are side-effect-free and resource-pure. The list mechanics live in `internal/server/httpx` (`PageRequest`/`ResolvePage`/`WriteList`) and are not re-implemented per route: `page_size` defaults to 50 when absent, maxes at 200, and out-of-range is a 400 `OUT_OF_RANGE` — never a clamp; an **explicit `page_size: 0` is the count-only read** — no items, `total_count` under the same filters (`stat()` on the directory instead of `read()`), which is why `PageRequest` decodes the field through a pointer: absent and zero are different requests; the token is opaque `base64url` (offset today, keyset later without a wire change) and carries a fingerprint of the canonicalized filters, so page 2 of one query can't be requested with page 1's token of another. `total_count` is the filtered total, and the store computes it under the same filters on the same connection as the page (`db.ListOpts` + `(items, total, err)`). Every list `ORDER BY` ends in an id tiebreaker — without a total order, offset paging drops and repeats rows that tie. A list read registers through `apiMutating` because it is a POST; reads-as-POST is deliberate for body-carrying queries (repeated query params are how one read drifts into two spellings with different hidden defaults), and CSRF applies to the method, not the intent. `POST /api/tasks/list` (`internal/server/tasks.go`) is the reference implementation.
- **Synthetic reads: a statistic is a file, not a query.** Numbers *about* rows — a series, a distribution, a share — get their own **node**: a read-only `GET` mounted under the resource it describes (`…/teams/{team_id}/usage`, `…/teams/{team_id}/activity`), windowed by strictly-parsed `?since=&until=`, with **no pagination** — the answer is bounded by its window, not a page, so `page_token`/`total_count` never appear on one. The response is a fixed schema of named cuts (`by_day`, `by_source`, `by_user`, …): never a `view=`/`group_by=`/`metrics=` parameter that changes the response shape — that is the one-intent rule's discriminator field wearing a query string — so a different derivation is a different path name (`/usage` vs `/usage/ops`), and a cut that grows too expensive to always compute splits into its own node, not into a parameter. Placement test: an answer containing rows, or the *count* of rows, belongs on the resource's list (filters + `total_count`, count-only via `page_size: 0`); an answer containing numbers about rows is a node. Two corollaries: no fixed-window statistic fields on resources (a resource read must not encode a window nobody chose — the window is the caller's), and the same node name serves the same cuts at every scope that mounts it (`/api/me/usage`, `/api/teams/{id}/usage`, `/api/orgs/{id}/usage`), which is what lets a caller who found a resource predict where its statistics live. `GET /api/teams/{team_id}/usage` (`internal/server/usage_handler.go`) is the reference implementation.
- **One error shape.** `{"errors": [{"reason": "SCREAMING_SNAKE_CODE", "message": "prose", "field": "optional"}]}` — always a list; validation reports *every* failing field, not the first. `reason` is a stable machine code; `field` appears only for payload-field faults; the HTTP status is blanket. No plain-text bodies on `/api/*`, no 200-with-error, no raw driver/upstream strings in multi mode. Statuses are principled and consistent across routes for the same fault class (including the 404-vs-403 disclosure rule above).
- **Updates are PATCH on the resource.** `PATCH /…/<resource>/{id}`, field-by-field: absent = keep, explicit `null` = clear (decode via `json.RawMessage` so the two are distinguishable — `repos_handler.go` is the reference). No full-replace PUT that's really a partial write, no POST-as-update, no verb route for what is a column flip, no per-route clearing dialects (empty-string sentinels, zero-means-null, fields that cannot be cleared at all).
- **The API is the whole product; the SPA is one client.** Assume every route is also driven headlessly — an API token, an agent, an MCP server built on this surface, a shell script. So no rule may exist only in the frontend. Anything the UI enforces before it calls — a required field, a length or range cap, a format check (email, slug, cron, URL), an enum the form offers as a fixed set of options, a trim, a combination it refuses to submit, a precondition behind a disabled button — the handler enforces too, and rejects with the same fault class it would for any other bad value. Same for values the UI supplies: a default a form pre-fills, an id it derives from the current view, a field it always sends — the handler defaults or derives it itself, so omitting it is valid rather than a crash or a silently wrong row. A rule the UI applies and the handler does not is not validation, it is a convention, and the first headless caller breaks it.

  Two corollaries. **The same rule on two routes is the same rule** — if create caps a name at 200 chars, rename and import and PATCH cap it identically; a validator that exists on one door and not its siblings is the same gap wearing a different hat, so put shared checks in one function both call rather than restating them. And **enforcement is not display**: the frontend keeps its checks for the fast, specific feedback a form should give, and may still special-case *presentation* freely — what to show, how to phrase it, which affordance to hide. It just may not be the only thing standing between a caller and a bad write.

- **The path is the address.** A route's subject is named in its path, and the scope segment is what the authorization check is about. The credential supplies the **tenant** — which org's rows this caller may see — never the **subject**: a route whose subject is a named org or team takes `{org_id}` / `{team_id}` and authorizes against *that value*, so a caller who belongs to three orgs can read all three without mutating anything first. That is also the precondition for token access, where there is no session cursor to move: `POST /api/me/active-org` is a session verb, and a route that depends on it having been called is a route a token cannot reach. Session-implied scope is reserved for **viewer-relative** subjects (`/api/me/…`, `/api/dashboard/…`), where there is no id to put in the path because the answer differs per caller and no caller may address another's — a `?user=` there would be an impersonation surface. Query-scoped narrowing (`?org=`) is the fleet console's alone: its subject is the deployment, and its gate is the operator flag, which does not vary with the value.

  A scope segment is what the answer **depends on**, not merely something the handler consults on the way: if two values of the segment would resolve the same row, the segment is a lookup key wearing an owner's clothes and the route is misaddressed. A per-user GitHub or Jira identity keeps its `{org_id}` on exactly that test — the org decides which host the identity is keyed under, and for Jira it owns the stored credential too — even though `user_github_identities` carries no `org_id` column of its own.

## Websocket events

Two tiers, and the default is the cheap one. The push economics are the opposite of REST's — cost scales with write rate × connected clients, not client interest — and unlike a REST read, the hub has no policy enforcement point: it scopes connections on `(org, user)` only (`pkg/websocket`), so any payload put on the wire must have its read policy hand-mirrored at emit time.

- **Invalidation ping (default).** A payload-free `<resource>_updated` event scoped by `OrgID`; the client refetches through the REST read, which carries the scoping. This is `tasks_updated`, it is safe under the org-only hub filter *by construction*, and it is the right shape for almost every "the UI should refresh" need. Reach for it first. A ping whose *audience* is narrower than the org still belongs here rather than in the tier below — it names what went stale and nothing about what changed, it just resolves who may hear it at emit time: `team_knowledge_updated` (`internal/knowledgeevent`) carries `(team_id, root)` as identity and lets the root decide, since the root IS the visibility — a `shared` change is one org-scoped envelope, a `private` one is fanned per team member on the `UserID` axis.
- **Sparse update (exception, by decision).** A payload-carrying event needs a stated reason — streaming (`message`), or field-wise merge where refetch-per-emission would thrash (`repository_updated`) — and then three requirements travel together: (i) a **typed Go struct as the explicit column allowlist**, never `map[string]any`, never every column (rows are dominated by bookkeeping — ETags, timestamps — nobody renders); (ii) **new values of just-written fields only** — no before-images, no row diffs, and emission stays at the write site where the delta is free (nothing emits from the store layer); (iii) **delivery scope mirrors the REST read's visibility.** For team-visible data that means resolving the audience at emit time and fanning out per user on the hub's `UserID` axis — `internal/repoevent` + `TeamGitHubRepos.RepoUpdateRecipientsSystem` is the reference. Do NOT capture team memberships on the connection instead: nothing kicks or revalidates a socket on team-membership change (only org-level removal kicks), so connection-side capture goes stale into exactly the disclosure the scoping exists to prevent. Emit-time resolution reads fresh per event and cannot. Toast bodies are payloads too: a toast naming visibility-scoped data (repo slugs, project keys) follows the same rule — resolve the audience and fire per user via `toast.FireUser` (the profiler's batch-failure toast is the reference).
- **Never CDC.** "An event per row change" is recorded as wrong here, twice over: the write rate is dominated by columns nobody renders (`pulls_etag` per repo per poll cycle, instance heartbeats every ~4s), and Realtime-style row broadcast is only safe when the stream itself has the read policy applied (Supabase applies RLS to it) — this hub cannot, which is why the allowlist plus emit-time scoping stand in for it. Wanting live-query semantics for real is a platform decision (a policy-aware sync engine), not an event-shape convention.
