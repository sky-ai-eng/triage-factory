GitHub interactions use `{{BINARY_PATH}} exec gh`. Run `{{BINARY_PATH}} exec gh --help` for the full command list, and `--help` on any subcommand for details.

Workflows:
- Inspect a PR: `exec gh pr view`, `exec gh pr diff`, `exec gh pr files`. Use `-v` for full review/comment bodies. `pr diff` does NOT print the whole diff — it persists it to `./_scratch/pr-diffs/<owner>__<repo>__<number>/<head_sha>/` (a `full.diff` plus a `manifest.json`) and prints the manifest JSON. Read/Grep the `full_diff_path` from the manifest instead of expecting the diff on stdout; the manifest's `files` array gives you per-file status and +/- counts up front. Pass `--file <path>` to print just one file's diff inline, or `--stdout` to print the entire diff inline. Re-running after the branch moves writes a new SHA-keyed directory, so an earlier capture stays valid.
- Reuse an already-captured diff in a multi-step run: the diff directory is keyed by the PR's head SHA, so if an earlier step of this blueprint already ran `pr diff` for this PR at the current head, the capture is still on disk — `ls ./_scratch/pr-diffs/<owner>__<repo>__<number>/` and Read the `manifest.json`/`full.diff` under the matching `<head_sha>` directory instead of re-querying GitHub. Only re-run `pr diff` if no directory exists for the current head SHA (e.g. the branch was pushed to since the last capture). Confirm the head SHA via `pr view`.
- Review a PR: `exec gh pr start-review` → `exec gh pr add-review-comment` (repeat) → `exec gh pr submit-review`. Tag each inline comment with `--severity <blocker|major|minor|clean>` — it renders a severity badge (BLOCKER / MAJOR / MINOR / CLEAN) on the posted comment; omitting it drops the badge silently.
- Open a PR for your work: ALWAYS `git push` first — even if you think the branch already exists upstream, push the local commits before calling `pr create`. `pr create` verifies the head branch is on origin via `git ls-remote` and hard-rejects when it isn't, because the human-approval overlay can't render a diff for a branch the server can't fetch. After the push, run `exec gh pr create --title <T> --body-file _scratch/pr-body.md --base <branch>`. Write the PR body to a file under `_scratch/` (you have free run of that directory) and pass `--body-file <path>` — for anything beyond a one-liner this is far more reliable than escaping a multi-line `--body "..."` heredoc. Pass `--body-file -` to read from stdin instead. The short `--body <B>` form still works for terse single-line bodies; `--body` and `--body-file` are mutually exclusive. Inside a delegated run this queues the PR for human approval — the user reviews the diff in the UI and clicks Open PR. Do NOT call `pr create` again after seeing the queued response; your work on this PR is complete. Standalone usage submits to GitHub immediately.
- Investigate a failing CI run: `exec gh actions download-logs <workflow_run_id>` downloads and extracts the full log archive to `./_scratch/ci-logs/<run_id>/`. Returns JSON with `run_id`, `owner`, `repo`, `dest_dir`, `bytes_downloaded`, and an `entries` array listing the top-level contents. Use your standard Read/Grep/Glob tools on the extracted files — each top-level directory under the destination is a single job.
- Read files in the working directory for context beyond the diff.

Repo target resolution:
- All gh commands target a (owner, repo) pair. Resolution order: an explicit `--repo owner/repo` flag, then the `TRIAGE_FACTORY_REPO` environment variable (set automatically for delegated runs with a resolved repo context), then the current directory's `.git/config` origin.
- You almost never need to pass `--repo` — the env var is already set for you when your run has a repo context.

Gotchas:
- `pr view`, `pr diff`, `pr files` all take `<pr_number>` as the positional argument. **`pr review-view` is different** — it takes `<review_id>` positional and the PR number as `--pr <pr_number>`. Review ids come from `pr view <pr_number> -v` -> `reviews[].id`. Canonical shape:
  ```
  {{BINARY_PATH}} exec gh pr review-view <review_id> --pr <pr_number> -v
  ```
  `pr thread-view` is also asymmetric: `<pr_number> <comment_id>` (two positionals, no `--pr` flag). When in doubt, run `--help` on the subcommand.
- The `--body` for `submit-review` should begin with a `##` title (e.g. "## Looks good — minor nits") followed by your summary. A top-level heading and metadata footer are added automatically; use `##` for yours.
- `submit-review` is the **last** call in a delegated review run. It queues your review for human approval rather than posting it to GitHub directly — the response will be `{"status": "queued_for_human_approval", ...}`. After you see that response, do NOT call `submit-review` again (the second call will hard-error). Write your `{{RUN_ROOT}}/_scratch/entity-memory/{{BLUEPRINT_RUN_ID}}/{{RUN_ID}}.md` memory file and return your completion JSON.
- For multi-line `--body` arguments, use a heredoc:
  ```
  {{BINARY_PATH}} exec gh pr add-review-comment <review_id> --file <path> --line <N> --severity <blocker|major|minor|clean> --body "$(cat <<'EOF'
  Your comment here.
  Can span multiple lines, include "quotes", and code blocks.
  EOF
  )"
  ```
  Or pass `--body-file <path>` (mutually exclusive with `--body`, `-` for stdin) — more reliable than a heredoc when the body contains backticks (e.g. a ```suggestion block), since there's no shell escaping. Works for `add-review-comment`, `submit-review`, and `pr create`.
