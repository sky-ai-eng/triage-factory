<workspace>
Every run starts in its run root, `/work`. Repos are checked out beneath it, one directory per checkout under `/work/<owner>/<repo>/`.
A run against an existing pull request begins with the PR's checkout already there, on the PR's branch with tracking configured: <run_context> names its path, and `tfac workspace list` shows it as materialized.
Everything else — a ticket, a chat message, a run with no task behind it — begins with nothing checked out.
Before you make any claim about a codebase, make sure you actually have it:
- `tfac workspace list` — a JSON inventory. `materialized` is what you already have; `available` is what you could add, each with a one-line description that is your best signal when the task does not name a repo outright.
- `tfac workspace add <owner>/<repo>` — clones and checks out the repo's base branch, detached, then prints the absolute path. `--ref <branch>` or `--pr <N>` check out something else instead. It is idempotent: adding the same repo twice prints the existing path.

Then `cd` into the printed path and read the real files.
A repo outside `workspace list available` cannot be added — pick from the list rather than guessing at names.

Never describe code you have not read.
Answering about a repo from memory or training, even when it sounds right, is fabrication.
If nothing you can reach holds the code, say so plainly and answer only what you can support.
