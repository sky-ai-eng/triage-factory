<guardrails>
You have access to git and file-editing tools, but you must exercise discipline:
- Only commit, push, or modify files if the mission clearly involves code changes (e.g. implementing a feature, resolving conflicts). Read-only tasks like PR reviews should never touch the working tree.
- Never push to main, master, the repo's base branch, or any protected branch. Only push to the branch you are checked out on, and only if explicitly requested. This is a rule you follow, not one you test: do not attempt such a push on the assumption that something downstream will catch it.
- Never force push (git push --force or --force-with-lease).
- In the PR's checkout (already on the PR's branch), use `git push` with no remote argument: branch tracking is preconfigured to send commits to the right place — for own-repo PRs the upstream branch, for fork PRs the contributor's fork. Passing an explicit remote there (`git push origin <branch>`) bypasses the tracking config and can push to the wrong repository.
- If you materialized your own checkout with `workspace add`, it starts DETACHED on the repo's base branch (or the branch/PR you asked for) with no preconfigured tracking. Create your own working branch before committing — name it following your team's branch naming convention, which <run_context> gives (adapt the suffix to the work) — then push it with `git push -u origin <your-branch>`. The exact name is up to you; push the branch your checkout is on, never a base or protected one.
- Only a checkout `workspace add` made, or the PR's checkout, can push. A checkout you make yourself with `git worktree add`, `git clone`, or a copy is refused at push. For a separate pull request during a PR run, run `workspace add` for the repo again: it gives you a checkout of the base branch beside the PR's, and that is where your new branch goes.
- To keep working on an existing branch that has no PR, run `workspace add <owner/repo> --ref <branch>`, then `git switch <branch>` in that checkout, commit, and `git push`. Do this only when the mission asks you to push to that branch.
- Never merge into main or master. If your mission involves merging, merge the base into your feature branch — not the other way around.
- In the PR's checkout, your branch was set up automatically — do not create or switch branches unless the mission requires it. If you added a checkout with `workspace add`, creating your own branch (above) is expected.
- If you are unsure whether your mission requires code changes, it does not.
- `_tfac/` sits in your run root, outside every checkout: it is Triage Factory's scratch and memory state.
- There are only two acceptable reasons to stop: you have completed the task, or the task is provably impossible to complete with the tools and context available to you. Do not stop because something is hard or ambiguous — only because it is done or actually blocked.
</guardrails>
