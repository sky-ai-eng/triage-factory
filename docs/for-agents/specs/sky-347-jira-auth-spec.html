The real picture is a 2×2: each backend authenticates a service identity (polling + autonomous bot work) and a per-user identity (actions a human takes) by different mechanisms. Cloud, without the developer console

Default Cloud onboarding touches nothing at developer.atlassian.com. The service identity is a bot API token (Basic, no app); the user side is OAuth through TF's first-party app — every org's users authorize one shared app and register nothing. The two are orthogonal: the service choice needs no app ever; only the user side needs one to exist.

  • whose appFirst-party (hosted, default) vs per-org (override). Per-org registration — customer pastes client_id/client_secret — survives only as the override, no longer the default.
  • flagged, not centeredSelf-hosted TF talking to Cloud Jira can't put its callback on our first-party app, so it falls back to a per-org app (or per-user API tokens). The uncommon corner — worth a line, not a load-bearing case.
  • policyAn org admin can disable API-token creation. If so, the service side falls back to an OAuth bot grant — so API-token service is the default Cloud service path, not the only one.
  • transportMixing means two transports on one Cloud site at once: service calls go Basic to {site}.atlassian.net, user calls go Bearer to the api.atlassian.com gateway. The client picks scheme and base-URL per principal, not per deployment.
02What the spike overturned

Cloud-first was backwards.

SKY-347 was written assuming Cloud OAuth first, with Data Center "likely v2" in the non-goals. The first customer self-hosts Jira Data Center inside an isolated VPC. That inverts the priority — and surfaces two findings about the code as it stands today.

⥂

The DC / Cloud priority flips

Data Center isn't a v2 deferral — it's the v1 first-customer path, and the cheap one: a service-user PAT is exactly what jira.Client already does. Cloud OAuth becomes the SaaS-tier follow-on, de-riskable against a test site but off the first-customer critical path. SKY-347 blocks SKY-410 (onboarding rework), so this reordering unblocks real work.

⚠

The client is Bearer + v2 only

Every request sets Authorization: Bearer against {baseURL}/rest/api/2/… (internal/jira/client.go, auth.ValidateJira). So a DC PAT connects — but a Cloud API token will 401, because Cloud wants Basic base64(email:token), not Bearer. Cloud support needs a pluggable auth scheme + v3, not just a new URL.

⚠

Today, the bot acts as a human

The org-level Jira credential is currently a person's personal PAT — so every autonomous transition TF makes is stamped in Jira history as that person. That's the credential-borrowing anti-pattern this ticket exists to kill, just inverted. First fix is cheap: provision a dedicated bot user and put its PAT at the org level.

✓

The identity half is already built

GetJiraIdentity exists, /api/me already returns jira_* fields, and the team roster carries JiraAccountID ("null when member hasn't connected Jira"). SKY-397's user_jira_identities table + store + exposure look landed or nearly. The read-mapping problem is solved.

+

What's genuinely net-new

Per-user credential storage; a RequireJiraIdentity gate; the Cloud per-org OAuth flow; and the DC per-user-PAT bind flow. Everything else is composition over what's there.

03Who makes the write

Two actors. One rule.

Per-user auth is mandatory — every user binds their own credential before taking a Jira action, with no "bot acts on their behalf" fallback. That splits the resolver into two provenance-keyed entry points. The service identity never stands in for a human; a human action never silently becomes the bot.

cool · the machine

JiraClientForSystem(org)

// polling · autonomous delegation · scorer
client := resolver.ForSystem(org)
// service credential only — never borrows a user
  • Drives the poller and any agent-initiated transition or comment.
  • Attributed to the bot in Jira history — which is exactly what you want for audit.
  • Source: the org's dedicated service account (DC PAT / Cloud bot token).
warm · the human

JiraClientForUser(org, user)

// claim on /board · user-authored comment
client := resolver.ForUser(org, user)
// user's own credential — guaranteed by the gate
  • Every user-initiated write. Attributed to that human in Jira history.
  • Credential guaranteed present by RequireJiraIdentity; if somehow absent, block the action — never substitute the bot.
  • Source: the user's OAuth grant (Cloud) or personal PAT (DC).

Not a fallback chain. A provenance switch.

This rewrites SKY-347 scope #5: the user credential isn't the last tier of a chain — for a user action it's required, and degrading to the service account is a bug, not a fallback. One user flow can legitimately emit both: you claim a card → your transition; the agent it spawns opens a PR → the bot's writes. That's the runs.actor split working.

04Why Jira costs more than GitHub

GitHub forces identity. Jira forces a credential.

We already force per-user binding — RequireGitHubIdentity hard-gates the app in multi mode and fail-closes on a transient check. But it captures a name. Jira's mandate is heavier: to attribute a write to a human, TF must act as them — a credential at rest, not just a string.

github · the precedent

Binds an identity

  • The connect flow captures your username → user_github_identities.
  • The org App / PAT still does all the API work. TF never acts as you on GitHub; writes are bot-attributed by design.
  • Storage held: an identifier. No per-user secret.
jira · the mandate

Binds a credential

  • User-initiated writes are attributed to the user → TF acts as them.
  • That requires a per-user credential at rest: an OAuth refresh token (Cloud) or a PAT (DC), keyed (user_id, jira_base_url).
  • Storage held: a secret — net-new custody beyond SKY-397's identity table, and real vault surface in multi mode.

Same gate. Heavier payload.

05How local mode holds the shape

Two slots, always — local just shares the value.

06The ticket's open questions

Four questions, answered.

SKY-347 listed four things to validate before the work is implementable. Here they are.

Q1Which Atlassian auth model fits TF's bot-identity needs?+
It splits by backend, not by a single choice. Data Center (first customer): a service-user PAT for the bot, a per-user PAT for each human. Cloud (SaaS): one per-org OAuth 2.0 (3LO) app — a bot-user grant for the service identity, real-user grants for each human. 2LO client-credentials for general Jira REST is not available; Connect and Forge are ruled out. verdict · PAT on DC, 3LO on Cloud. No single mechanism spans both.
Q2Is there a per-org registration flow — a GitHub-App-manifest equivalent?+
No. Atlassian has nothing like the GitHub App manifest auto-create. On Cloud, an org admin manually creates an OAuth 2.0 app in developer.atlassian.com and pastes client_id / client_secret into TF — that's the worst case, and it's the only case. On DC there's no app registration at all: PATs are minted in user profile settings. verdict · manual app creation on Cloud; nothing to register on DC.
Q3What's the site-authorization shape?+
Cloud 3LO returns a cloud_id per authorized site; one app can be authorized across many sites, and tokens are routed through api.atlassian.com/ex/jira/{cloud_id}. So org_jira_site_authorizations(cloud_id, …) is a Cloud-only table. DC has no cloud_id — the base URL is the host, so multi-site there is just multiple host URLs. verdict · cloud_id is real, and Cloud-only. DC addresses hosts directly.
Q4Does this need to handle Data Center, or just Cloud?+
Data Center, first. The first enterprise customer runs self-hosted Jira DC inside the same isolated VPC as their corp git — so DC is not the deferrable case the ticket assumed, it's the v1 case. The good news is it's mostly already working (Bearer + v2). Cloud OAuth is the genuinely new build, scoped as the SaaS-tier follow-on. verdict · DC is v1 and nearly done; Cloud OAuth is the follow-on.
