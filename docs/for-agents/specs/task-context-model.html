Task context model: conversations, boundaries, memory, and the shared workspace

A task owns its conversations, its workspace, and its artifacts, and they follow it across every handoff. A conversation is one mission; a small closed list of boundaries ends one and records its memory; whoever engages next opens a new conversation with the task's prior memories injected. Messages are never boundaries. There is no "clear": the transcript, the memory, and the pushed work are the durable record, and context is bounded by the rules rather than by deletion. Every mechanism below already exists for one blueprint run's steps; this widens it from the run to the task.

§0

The rules

Six rules. Every case in §13 falls out of them; nothing below adds a case.

  1. A task owns its workspace, its artifacts, its visibility, and its conversations in order. The workspace is keyed by task, not by blueprint run. The conversations are ordered, and each boundary is recorded on the row it ended, so a surface can render them as one sequence — the run station redesign that will is blocked on this spec and is not part of it (§15). A new task is a new workspace, even on the same entity.
  2. A conversation is one mission. A blueprint step is one; a human's own engagement with the agent on a task is one. It ends only at a boundary (§4). Steering it, resuming it, and reassigning the task's user claim never end it.
  3. A conversation records one memory when it ends. The agent's own, if it reached its completion gate; a generated one, if a boundary ended it first. The row is conversation_memory, per conversation, per entity, exactly as today; what changes is that every ending writes one.
  4. Resume when no boundary has passed. A message into the task's latest conversation continues it with its full context — steer if live, resume if parked or completed — exactly today's composer. User→user reassign moves the claim and leaves the conversation for the new claimant to resume.
  5. Otherwise open a new conversation with the task's memories injected. Every blueprint step, and every engagement after a boundary, opens a new conversation whose opening turn carries the task's prior conversation memories in order (today's this-run/, widened from the run to the task and injected inline rather than left as files). The entity's other tasks' memories stay as history/ files to read.
  6. Requeue is stop, record memory, back to the queue. No Keep, no Clear. The parked conversation stays readable with its composer closed and the reason named; the next claimant opens a new conversation under R5. Artifacts are untouched.
Why this is small. A blueprint run already enforces "one workspace, one drivable conversation, only the current step resumable" (internal/delegate/followup.go:296 — "an earlier step is never resumable, because the blueprint's one workspace has moved past it"; blueprintDrivableSQL, internal/db/postgres/conversation_queue.go:198-228). Step N+1 already starts fresh in the shared tree with step N's memory materialized. The spec generalizes that invariant from run to task and adds the boundaries that retire the latest conversation when the task, not the blueprint, moves on.
§1

Why now

The Board redesign asked for a requeue dialog with a "keep or clear the conversation" choice. Scoping it against the code showed that neither branch was implementable as drawn, and that the question underneath it was the wrong one.

  • "Clear" as a message delete is a cap bypass. messages is the spend ledger — llm_spend is a view over it (202605130001_pg_baseline.sql:5296-5337), the daily cost cap sums that view (internal/delegate/cost_cap.go:60-63), and every usage node reads it. Deleting a conversation's rows refunds the org's day. It is also the pending-input queue and the staged-injection store, and the executor role holds no DELETE on it by design (:5355-5358).
  • "Keep" as artifacts-survive-on-a-queued-task reached seven readers that assume a queued task holds nothing outstanding, and the very next delegation tore the kept artifacts down anyway (internal/server/task_actions.go:457).
  • The premise was per-run. The handoff treated a conversation as a run's transcript. A human who drags a task to Claimed and talks to the agent, then delegates, then hands off to a teammate, has one piece of context moving through three hands. The blueprint reactor already models that for its own steps; nothing modelled it for the task.

So instead of a dialog, this: define what a conversation is, what ends one, and what the next one starts with, once, for every handoff in the system — user↔user, user↔blueprint, step↔step, and the task gestures — then build the Board's requeue on that.

Not boundaries

  • Messaging a live conversation — steer. The task's claim does not move; a human steering a bot-claimed run is still a bot-claimed run.
  • Messaging a parked or completed conversation — resume, today's rule, including the current-step restriction (isCurrentBlueprintStep, followup.go:296).
  • Pause, permission prompts, parks — the conversation is open and resumable.
  • User → user reassign (within the task's owning team, §14) — the claim moves, the conversation stays; the new claimant resumes it. messages.user_id attributes each row; RLS on conversations is team-scoped (baseline:2367), so a teammate can read and post.
Why takeover is a boundary by construction. A human claim and a running blueprint cannot coexist (the claim axis is XOR), so the takeover cancels the blueprint (task_actions.go:627), and a cancelled blueprint's step is unresumable by the existing rule (blueprintCalledOff, followup.go:213-217) — necessarily, since a human resuming it and ending a turn with continue would have the reactor fire the next step on a human-claimed task. Messaging the run while it stays bot-claimed is steering; the picker is the person saying the bot's attempt is over.

Why requeue is a boundary and reassign is not. Both are ways to engage with the full context, and both are deliberate: a person who wants the running or finished conversation messages it, or hands it to a colleague by name. Requeue is the opposite statement — this attempt is over, the task goes back to the pool — and days may pass before anyone picks it up. Dropping the next claimant into a stale window would surprise them; starting them on the recorded memory is what "back to the queue" means.

Why task end is not a boundary. A blueprint that finishes leaves its last step for a person's follow-ups, and a person's own conversation on a task can be mid-engagement when an event closes the task under it — an auto-close is a contract outside TF's control. So task end stops a live run (today's teardown) and ends nothing: the newest conversation stays exactly as the stop or the gate left it, resumable by the rules above, and owes no memory. A done task's conversations carry a memory only if they concluded through the gate.
§5

Context at a new conversation

What the model sees when a conversation opens, by runtime. The opening turn is the only thing that changes; the framework prompt stays byte-identical per Spec.

Today

Native: the system prompt is agentprompt.Build(nativeSpec()) (or the non-terminal variant), and mintOpeningTurn writes one pending user row — <run_context>, <task_context>, the step wrapper mission — gated on an empty transcript (native_run.go:265-330). SDK: the same sections plus <tools> and the framework prompt travel as the first user message (prompt.go:179-188). Prior memory is materialized as files under _tfac/entity-memory/{this-run,history}/ and the wrapper tells the agent to read them (blueprint.go:385-387).

Under the model

  • this-task, injected — one role='user' row per prior memory, rendered to the wire as one envelope. Before the task-context row is minted, the loop inserts one delivered row per prior memory on the task, oldest first: subtype = 'injection:memory' (a new member of the existing loop-authored vocabulary beside injection:steer / injection:nudge, internal/domain/agent.go:118-160, so the drain and the notice dedupe treat it as system-authored), content = the memory's agent_content — the memory text and nothing around it — and metadata = { "memory_id" } and nothing else: the conversation_memory row already carries conversation_id, entity_id and blueprint_run_id, and the conversation row carries prompt_id, its step index, and how it ended. Copying any of those into the metadata would be a second spelling of a column one FK hop away, and a prompt_id in particular would name a user-editable, soft-deletable prompts row rather than the text the step ran, which is frozen in blueprint_runs.step_plan. The memory row cascades with its conversation, so the key cannot dangle. Rows rather than a rendered section, deliberately: the transcript is what the run page reads, and one row per memory with a foreign key back to its source is a shape a surface can render as a card that links to the original conversation, without the frontend parsing a blob. The alternative (reconstruct at read time from conversation_memory through the task, inserting nothing) is rejected because it makes what the model saw a function of a later join rather than of the transcript; a transcript must be its own record.

    What the model sees is not N messages. Assembly already packs adjacent user rows into one wire message: consolidateAdjacentUsers (internal/inference/assembly.go:82-131) merges every run of adjacent role='user' messages into one message carrying their content blocks in order, because the API rejects back-to-back user turns. It merges by adjacency in assembly order — COALESCE(seq, id), the row order — not by subtype; subtype only decides per-row wrapping (wrapSteer, assembly.go:276-301, brackets an injection:steer row in its <steer> tag). So the order the model reads is the order the loop inserted: memory rows first, task-context row last, and the merge folds them into a single user turn. What is missing today is the framing. A run of bare memory texts followed by the task context reads as N unlabelled documents, so assembly gains a second subtype-driven wrapper beside wrapSteer: the maximal run of adjacent injection:memory rows is bracketed as a whole — one opening block before the first, one closing block after the last, each memory its own block between them — and then consolidated with the task-context row that follows. The wire shape of the opening turn is exactly:

    <system-note kind="task-memory">
This task has {K} prior conversations. Their memory files are at _tfac/entity-memory/this-task/ and are injected below, deliberately, so you do not need to read them. Memories from other tasks on this entity are at _tfac/entity-memory/history/ and have not been included.

{memory 1}

{memory 2}

…
</system-note>

{the <task_context> row}

    The wrapper is a pure function of the rows, like wrapSteer: {K} is the count of rows in the run (what was injected, not the task's total — under the §14 budget the folder may hold more than the turn does, which is what the second sentence is for), the two paths are the fixed relative paths every run tree presents (worktree.EntityMemoryDir, today's this-run widened to this-task), and nothing per-run enters the text, so two executors assembling the same rows build the same bytes. An elided memory row keeps its place in the run and renders as the [elided] stub inside the envelope; once compaction marks the run inactive there is no run, so no envelope. The wrapper lives beside wrapSteer in internal/inference, and the SDK path reaches it by calling RowsToMessages over its own rows (below), so there is one renderer with one caller shape rather than two paths kept equal by care. Persistence stays row-granular — K rows, each carrying its source key — while the provider sees one note; what a surface draws from those rows is the run station redesign's (§15). The moving cache breakpoint lands where it does today, on the last block of the merged message, which is the task-context block.

  • The mission moves to the system prompt, on both runtimes. Today the native system prompt is Build(spec) alone and the opening user row carries <run_context>, <task_context> and the mission (composeNativeOpeningTurn, native_run.go:323-330); the SDK path puts all of it, framework prompt included, in the first user turn (buildPrompt, prompt.go:179-188). Under the model the trusted sections — the framework prompt, the step wrapper mission, <run_context>, the tools reference — are appended to the system prompt on both runtimes. A manual conversation (§9) has no mission: its block 2 is <run_context> and the tools reference, and the human's opening message is an ordinary first row, because a human's messages are the transcript and the first one is only the oldest.: native as a second system block after Build(spec), SDK through the claude_code preset's append the wrapper already wires for --append-system-prompt (wrapper.mjs:88-97).
  • Cache mechanics, stated exactly. Today the native system prompt is one text block with one ephemeral breakpoint on it (withSystemCacheBreakpoint, internal/inference/cachecontrol.go:40-50); the cached prefix is tools + that block, shared across every conversation on the same model and tool schemas within the org's cache (the account and region on Bedrock). Appending per-conversation text into that block would end the only cacheable prefix after the per-conversation bytes and the framework prompt would never be shared again. So the system prompt becomes two blocks with one explicit breakpoint: block 1 is Build(spec) carrying the marker (the cross-conversation entry — explicit, because a cache entry exists only where some request placed a breakpoint, and the provider's own docs name "breakpoint on the varying block, no entry ever written at the static prefix" as the common mistake), block 2 is the per-conversation sections with no marker. The breakpoint count does not change: block 1's marker plus the moving conversation breakpoint, two of the provider's four, exactly what cachecontrol.go places today. Block 2 needs no marker of its own, and the reasoning is worth stating because the first draft of this spec gave it one. Writes happen only at breakpoints; reads check the breakpoint, walk back up to 20 block boundaries for an entry an earlier request wrote, and on a miss resume at the next explicit breakpoint. On the first turn the moving breakpoint writes one entry covering tools + block 1 + block 2 + the opening turn, and every later turn's lookback finds the previous turn's entry, so block 2 is read at cache-read price on every turn as part of the conversation prefix — the same cost shape a block-2 marker would give. A marker on block 2 would write an entry at a position only this conversation can ever match, and this conversation's later turns already match a longer one. The two cases where block 2's own entry would be the highest hit are both marginal: a turn that added 20 or more blocks (a batch of ten parallel tool calls does it) makes the lookback miss the conversation entry and resume at block 1, and a block-2 marker would move that fallback forward by block 2's few thousand tokens while the conversation is re-written either way — the fix for that case, if it is ever worth a slot, is a second moving breakpoint on the previous turn's last block, which makes the lookback exact; and an idle gap past the TTL expires block 2's entry together with the conversation's, since they were written at the same moment under the same TTL. Billing is by segment between breakpoints, so a nested marker would not double-charge; it would simply do nothing. Bifrost carries the shape: the Anthropic packer maps a system message's ContentBlocks with per-block CacheControl (providers/anthropic/chat.go:649-690); Bedrock keeps cache points on supporting models and strips them otherwise. withSystemCacheBreakpoint takes the two blocks instead of a string and stamps the first, not the last — stampLastBlock on a two-block system message would put the only system entry after the per-conversation bytes and the shared entry would never be written; that is the whole inference-side change, and the test that pins it asserts the marker's position, not its presence. Existing caveat, unchanged: tools precede the system prompt in the prefix, so block 1 is shared only among conversations with identical tool schemas. On the SDK, captured on the wire on 2026-09-10 (a local capture server, body shape only): the append is a system-role block — the request's system is an array of three text blocks (a billing line; a 94-char preamble with a 1h ephemeral breakpoint; a 27k-char block carrying Claude Code's instructions, its dynamic sections and the append, with its own 1h breakpoint) — never a user message. Claude Code does inject its own <system-reminder> text blocks ahead of the prompt in the first user message, which is how it delivers skills, agent types and CLAUDE.md, not how it delivers append. Measured across three sessions with two different appends: the ~16.5k tokens read from cache every session are the 67 tool schemas plus the two short blocks (cached at the preamble's breakpoint), and the ~7k written per session is the third block, which is per-session regardless of TF because it carries the date, cwd, git state and loaded instructions. The append shares that block, so it costs nothing cross-session that was not already per-session. Two notes for the ticket: Claude Code uses a 1h TTL on its breakpoints where the native path leaves the 5-minute default (cachecontrol.go:17-19 already marks the TTL a policy decision); and dropping the append on resume makes the third block differ between a session's first and resumed turns — a cache miss on top of the missing mission. The untrusted <task_context> — "built entirely from external data" (prompt.go:170-172) — stays a user row on both, because putting attacker-influenced text in the instruction channel is a trust-posture change. Order of the opening user turn on both: memory rows, then the task-context row.
  • Nothing is pinned through compaction, on either runtime. Today a delegation runs MissionAnchored: true (native_run.go:211) and compactionSpan (internal/agentloop/compact.go:350-368) pins every leading row before the first assistant turn, so the mission survives every compaction verbatim; a taskless conversation runs unanchored and composeResultRow re-injects its first human row as <original_request> instead (compact.go:427-447). The pin's reason — "the summary can never mutate the task" — is served by the system prompt once the mission lives there, and the SDK has no pin to offer, so keeping one on native would make the same task behave differently after a compaction in local and in multi. So MissionAnchored and the anchored arm of compactionSpan are deleted, not rewritten: every conversation takes the one remaining arm, memory rows and the task-context row compact like any delivered row, and the previous summary compacts into the next so nothing accumulates. What survives is retained, not re-sent. The mission is in the system prompt, re-sent every turn and never summarized. The task context is retained by reference on both runtimes: the launch writes it to _tfac/entity-memory/task-context.md — inside the staged memory tree, the one per-launch location that is still writable on a warm, handed-off step, where the tree itself is not, the mission block names that path, and an agent whose summary lost a PR number re-reads the original. Compacting the task context is also the better posture — it is externally authored text, and a pin would carry it verbatim into every window for the life of the conversation, where the summary is the model's own restatement. One consequence has to be handled: originalRequest (compact.go:454-470) picks the first row IsHumanInput admits (subtype empty or injection:steer, drain.go:70-72), and today's opening turn is minted as a plain user row (mintOpeningTurn → pendingUserInput, native_run.go:265-275) — with the pin gone it would be re-injected into every result row, which is the pin under another name and worse, since the text is untrusted. So the task-context row carries its own subtype, injection:task-context: originalRequest skips it structurally, and it is the same discriminator the three row-counting gates below key on. A manual conversation's opening message keeps its empty subtype, so the existing <original_request> re-injection applies to exactly the conversations it was written for. Consequence stated plainly: the mission stops being a transcript row on native; the transcript holds the task context and the memories, and the mission is readable as the blueprint's prompt.
  • history, as files. The entity's other tasks' memories keep today's history/ materialization, untouched. This task's non-empty memories are also materialized as files (this-task/, today's this-run/ widened), so a memory that falls outside the injection budget is still readable on request. The split predicate moves from blueprint_run_id to the conversation's task_id, read through the join (§11).
  • Budget. A count-and-size cap on injected rows, newest first, contiguous, whole rows only — the newest 5 within 32 KiB (§14). Memories past the cap are files only; nothing folds or truncates inside a row.
  • Native gates that count rows must learn the new subtype. Three predicates answer "has this conversation started?" by looking at rows, and memory rows precede the mission: mintOpeningTurn mints only when len(rows) == 0 (native_run.go:265-277); conversationHasTranscript (dispatch.go) decides fresh-versus-resumed from ListForAssemblySystem, and its own comment says a wrong answer "destroys its workspace and fails its blueprint"; prepareInheritedMemory (native_run.go:364-384) clears the agent memory file when nothing has been driven. Each becomes "is there an injection:task-context row yet", not "any row" — one subtype check, the same discriminator compaction uses. Missing one is a silent-non-claim or a wiped memory file, so all three are named in the ticket and pinned by test.

The SDK path, verified

Read from the wrapper (internal/agentproc/wrapper.mjs), the Go side (agentproc/live.go, stream.go), the installed @anthropic-ai/claude-agent-sdk 0.3.195 (sdk.d.ts), and a smoke run against that SDK on 2026-09-10 (nine sessions, claude-haiku-4-5, scratch script; the shapes and counts below are what it produced). No shouldQuery, no ordered initial send, no wrapper filtering. The block boundaries match too — send blocks, never a joined string, or the text would match and the shape would not.   • shouldQuery: false, verified and set aside. Recorded so nobody re-derives it. SDKUserMessage.shouldQuery (sdk.d.ts:4241-4244) appends a message to the transcript without an assistant turn, merged into the next querying message. Observed in nine sessions: N non-querying messages then one querying message produce one assistant turn (9 of 9); the session file holds N+1 user entries chained by parentUuid, flag not persisted; the model reads them as one turn; --resume replays them; no user echo on the output stream. Also observed: each non-querying message emits a system:init and a result:success with num_turns: 0 before the real turn, which TF's reader would count as a completed turn (stream.go:206-211). It would be the mechanism if the opening turn were more than one message. It is one message, so none of that ships.
  • Divergences that remain, named. Everything below is the harness, not the opening row, and each is listed because the rule is that a divergence is reported, never absorbed. §6

Memory at a boundary

R3 says every ending writes a memory. Today only the completion gate does. This is the one new piece of machinery.

  1. The agent's file is already in the row._tfac/memory.md is mirrored into conversation_memory (source = agent) as the agent writes it: the executor re-reads the file after every tool call on both runtimes (the native loop's AfterToolCall hook, the SDK driver's message sink) and files it through the existing upsert (UpsertAgentMemorySystem) whenever it changed and is not the previous step's inherited copy, with a final read at every park, conclusion and failure. The file is durable only on the executor's disk between snapshots, and a boundary stamped on a control pod cannot read that disk — so nothing at a boundary reads a file: a conversation with a row has the agent's latest words, and one without has an agent that never wrote.
  2. Generate when there is none.A toolless call through internal/systemllm on the org's background-jobs model, summarizing the conversation's transcript into agent_content — it names the commits, the branch, the PR, and what was mid-flight, which is what the next conversation needs to make sense of a tree it did not build — recorded in system_llm_runs like the scorer's cycles. Prompt text lives beside its consumer (prompt-ownership rule). It runs where the transcript is: the control plane for a requeue or takeover (the handler has the rows and the credential), the executor's own teardown for a step the reactor ended.

    Windowing, therefore. The generator never sends the whole transcript. It fills a fixed input budget — 100k tokens by a bytes/3 estimate, conservative against Claude Code's estimator and small enough to leave the same headroom on a 200k window in either mode — as head plus tail: the opening turn first (the task-context row and the memory rows, which name the task and the prior state), then rows from the newest backwards until the budget is spent, with the elided middle replaced by one marker line carrying the count of rows dropped. The tail is where the state a memory needs lives — the branch, the last commits, what was mid-flight — and the head is what makes the tail legible. The same function serves both runtimes: a native transcript may already carry a compaction result row, which is a row like any other and rides along in the tail; an SDK transcript is the raw mirror with no summaries at all (nothing in stream.go records Claude Code's compaction events), so the tail rule is the only thing bounding it. A memory generated from a window says so in its first line, so a reader knows it is a reconstruction.

  3. Nothing to remember: the empty row.A conversation that ends with no assistant row at all — failed before the model's first turn (a task that would not load, a step plan out of range, a sandbox that never came up: the terminateBlueprint failures in dispatch.go:310-547), or cancelled while still queued — has nothing a memory could hold, and generating one anyway produces a paragraph about a task that was assigned and not started: not memory-worthy, and a wait for nothing. The failure's reason is not memory either. It is on the conversation already (the failure row failConversation inserts, the failure kind it marks) and is the person's to read, not the next agent's to be told. So the provisioner's fulfil reads the transcript before anything else: no assistant row → it writes the empty memory row mechanically — agent_content NULL, source = none — with no model call and no wait; presence clears memory_pending, and an empty row is never injected and never materialized (the §5 budget walk and the this-task folder skip it). That is the shape the store already has: UpsertAgentMemory with no content writes a row with NULL content, and the concluded path's own comment reads it as "the conversation terminated; the agent wrote no usable file". One race is accepted rather than closed: a final mirror check that lands after the provisioner already generated overwrites the generated row with the agent's own file (the upsert replaces) — one wasted call, converging on the agent's words.
  4. Owed at every boundary, and the task is blocked until it lands.A boundary that ends a conversation without the agent's own file — requeue, takeover, a reactor-ended step, a failure — leaves that conversation owing a memory, and generation is kicked at once wherever the transcript and a credential are together. The state is derived, never stored: memory_pending on a task is "an ended conversation on this task with no conversation_memory row" — both facts already exist as rows, and a column beside them would be a third that can disagree. While it is pending nothing new opens on the task: the composer lets the person type and disables Send, showing the state, and the memory's own slot — above the boundary separator, where the ended conversation's memory renders once it exists — shows a skeleton until it lands (that slot belongs to the run station redesign, §15, and is recorded there so it is not lost); whatever route opens a conversation on the task — the manual one is TFAC-378's to define (§15) — refuses while it is pending (409 MEMORY_PENDING) rather than waiting, since a request that sleeps for a generation is a request that times out and retries into a double mint; and the dispatcher does not claim a queued delegation on the task, so a requeue-then-delegate waits the same way. The invariant this buys is the reason to block at all: a new conversation never opens without the memory, so nothing ever has to receive a late memory as an injection into a run already in flight, and at most one conversation per task can be owing at any moment — a second boundary needs a second conversation, which cannot open. task_updated fires when the memory lands and the composer re-enables. Measured (§6 table), the person waits 10–18 seconds in local mode from the drag, most of it spent typing. Per attempt the bound is an explicit 90 seconds (the scorer's calls carry no timeout today, so there is none to borrow). A failed attempt leaves the task pending and says why: every fulfil writes a conversation_memory_attempts row (below), and the owing conversation's newest one carries the outcome and, on failure, a classified error_kind with a TF-worded message — no background model configured names the setting, a provider error names the provider. There is no retry verb: generation is a system job, and a person-facing trigger for one would be a second spelling of "the sweep will get to it". The one cause a person fixes is org configuration — the background-jobs model, a credential — and the save of that configuration is the re-kick: the settings and credential save handlers ring the memory_owed doorbell for the org with no conversation id, which the provisioner reads as "re-sweep this org now, ignoring backoff" — the sources_changed precedent, a config save nudging the brain (those handlers do not nudge it for this today; it is one publish each). Every other failure class is one a retry-now would not help: a provider outage hits the breaker, a timeout re-runs the same window. Who fulfils it is the credential provisioner's shape exactly (internal/credprovision): a brain-owned memory provisioner, constructed only by startBrain/stopBrain, holding the only in-flight set — the brain is one pod, so "an attempt is in flight" is process state there and needs no column, and a demoted leader's stopBrain cancels its attempts before a successor can start one. Three ways in, all landing on one idempotent Fulfil(orgID, conversationID): the fast path is a memory_owed doorbell over tf_ctl (a new ctlbus.Message kind beside cred_request, which is the precedent — an executor nudging the brain about a row it cannot act on itself) published by the requeue and takeover handlers on any control pod and by the executor's reactor for a step it ended; the backstop sweep on the brain, every 5 seconds like DefaultAwaitingSweepInterval and for the same reason (it gates a person's Send), selecting owing conversations by the derived predicate — ended, no memory row — with no attempt in flight and the last attempt older than the bound (in-flight is process state on the brain — a crashed attempt's unfinished row must never read as still running — while the last attempt's time is the newest attempt row's started_at, so the backoff survives a brain restart); and the org-wide doorbell a configuration save rings. The relay is lossy by design, so the sweep is the completion path and the doorbell only shortens it; nothing is durable in the relay and nothing needs to be. Owing conversations on open tasks are swept first, since those block a person; a closed task's still owe (the memory is entity history for the next task) but block nothing. Local mode is the same code at N=1 — one process, always the brain, no relay. The block is narrower than it reads: takeover, requeue, complete, dismiss, and reading the tree and the transcript all work while the task is pending — only the two verbs that need a model, talking to an agent and delegating, wait, and a memory the generator cannot produce is usually a conversation the model could not have held either. Usually, not always, and the exception is a deadlock unless it has an exit: the background-jobs model and the conversation's model are separate settings that can sit on separate providers, so the failed run's provider can be healthy while the generator's is down, and a fresh multi org can have no background model configured at all. Transient faults are the provisioner's to outlast: it rides the systemllm breaker (IsProviderBackoff), so a provider in backoff is left for the next sweep rather than hammered, and the attempt row names it (error_kind = provider_backoff) so the task read can say what it is waiting on. A fault the sweep cannot outlast — no background-jobs model configured, a credential that no longer resolves, a provider that stays down — keeps the task waiting, and that is the answer rather than a gap: background jobs working is the steady state every deployment is assumed to hold (the scorer and profiler already stop silently without one), so an org in that condition has a configuration error to fix, not a task to unblock, and a waiver would only let the person walk past the error into a conversation missing its context while the error stays. There is deliberately no waive verb and no without_memory field on the mint. What the condition needs is to be seen: the owing conversation's newest attempt row and memory_pending on the task are the per-task signal, and a generation failure that persists is exactly the kind of quietly-wrong condition the durable-notifications epic (TFAC-878) exists to surface to an admin — it is recorded there as a consumer, and until it ships the composer's state text and the WARN the provisioner logs on every failed attempt are what there is. Nothing here is a stand-in that epic retires: the attempt rows are the per-attempt facts, and a notification is a coalesced condition opened from such rows (first-seen, last-seen, closed when an attempt succeeds), the same relation poll_readiness rows have to the toast read off them. The classification a condition needs is error_kind, stored per attempt where the provisioner handles the Go error, so the epic reads rows rather than log lines.
  5. Every fulfil is a row.conversation_memory_attempts, beside conversation_memory and conversation_memory_entities: one row per fulfil the brain runs, in both dialects. org_id; conversation_id with the same cascading FK the memory row carries; started_at; completed_at, NULL while running and left NULL by an attempt whose brain died — abandonment is derivable and never stamped; outcome generated | empty | failed, NULL until completed; error_kind no_model | provider_backoff | provider_error | timeout | other with a TF-worded error_message, never an upstream body, both NULL unless failed; system_llm_run_id, a nullable FK (ON DELETE SET NULL) to the call's cost, tokens and duration when a call was made, rather than copies of them; and window_rows_total / window_rows_sent, the windowing facts nothing else records. Admin-pool writes by the brain, app-pool reads, org-scoped RLS like system_llm_runs. That table alone cannot be the ledger, which is why this one exists: an attempt refused before any call — no model, breaker open — has no outcome, so Record no-ops and writes nothing, and a row it does write carries only is_error, no reason and no indexed conversation. The agent-file path writes no attempt: it is an executor-side read with nothing to try, and "how often the agent writes its own file" is already conversation_memory.source. What the table makes derived: the reason a task is waiting is its owing conversation's newest attempt, exposed on the task read (§12), with no column on conversations; the sweep's backoff is that row's started_at. Analytics come for free — attempts per conversation, generated-versus-agent share, wait from a boundary to its memory (completed_at minus the conversation's ended_at), failure rate by kind, how often windowing elided rows, and spend per attempt through the join.
  6. Mark provenance.conversation_memory.source = agent | generated (§11). A generated row is overwritten if the conversation is later resumed and concludes — the upsert already replaces agent_content.
  7. Remove human_content; artifact outcomes are read, not stored.The earlier draft of this spec called human_content "the way a person annotates a memory". That is not what it is. Checked at 95385f49: no person ever types into it, no UI reads or writes it (nothing in frontend/src references it), and its five writers are all machine-composed verdicts about artifacts, keyed to the conversation the artifact row pins as its creator — a draft PR approved (formatPRHumanFeedback, the title/body diff, artifacts_handler.go:742), a draft PR rejected (a canned outcome-and-implication block plus the rejected title and body, :998), a staged review submitted or dismissed (the review-edit diff, reviews_artifact_handler.go:517), the artifact teardown at a disposition (buildDiscardHumanContent, five canned notes keyed by which verb discarded it, tasks.go:1536), and the reconciler's post-run outcome, which overwrites the whole column with the artifact set's terminal picture once GitHub reports a merge or close (reconcile.go:360-378). Its one reader concatenates it under a fixed heading into the memory text the file materializer and tfac exec memory load hand the agent. Under this model it is stale three ways. Attribution: artifacts carry across a task's conversations (§8), so a verdict on a PR that three conversations pushed to lands on the first one's memory, and injected in order it reads as a reaction to work that had not happened yet. Timing: the verdict is written whenever a person acts on the artifact, which is usually after the memory was already injected into a later conversation as a messages row — the snapshot is stale the moment it is taken, and the overwrite semantics also lose every verdict but the last. Redundancy: everything it records is on the artifacts row already (state, and details_json holding the proposed snapshot the diffs are computed from), and the PR's fate is on the PR entity's snapshot and history skeleton. So the column, its two store methods and the five writers go, and what the next agent still needs reaches it through two channels: now (new) — the opening turn's <task_context> gains the task's artifacts with their current state (kind, target, state, URL), which is task data and untrusted like the rest of that section, so a new conversation on the task knows what it inherits; and later (exists, unchanged) — a resolution after the turn opened reaches a live run as the artifact-feedback <system-note> and a parked one on its next follow-up (artifact_feedback.go, addressed to the conversation that made the artifact). Entity history carries the agent's memory only. A derived "artifacts beneath the memory" render for history files was considered and rejected: from the rows it can say one line per artifact — kind, target, state — and nothing more, since the reconciler's merged-title diff is fetched live from GitHub at merge time and the approval diff is against a final title the row never stored; for a PR entity that line duplicates the entity snapshot and skeleton, and for a ticket or thread entity the memory names the PR and the agent has gh pr view. What is genuinely lost is the reconciler's post-run diff — the one informative thing the column held — and if it matters its home is a stored final snapshot on the artifact row, a separate decision, not a memory column. The teardown's canned "implication" prose is the one thing not carried: it told the next agent what a discard meant, and under §8 teardown only happens at task end, where the state itself (a closed PR on a done task) says the same thing. The "bad run" case the earlier draft assigned to this column is served by the manual conversation instead: a person who wants the next agent to know "do not retry X" says so in the conversation, and it becomes transcript and then memory — which is the model's whole point.
  8. Human conversations write memory too — by guidance, checked by the transcript, never by cadence.A manual conversation has no completion gate, so the question is how its _tfac/memory.md stays current. Three ways were weighed. A cadence — a reminder every N user messages — is rejected: the count says nothing about whether work happened, so it fires through a ten-message discussion that changed nothing and misses the one message that produced three commits, and a reminder the model learns to ignore is noise in every transcript after it. A would-stop nudge on every yield — the mechanism artifactContractNudge already uses on native (native_run.go:453-496, re-armed by human input, read from the transcript) — is rejected for the steady state: it costs a full extra model turn each time the agent yields to the person, which in a conversation is every turn. What ships is the cheap path made common and the correct path made certain. Guidance: the workbench surface's memory block (§9) says to update the file when a piece of work is finished — a commit, a push, a decision, a dead end — and not per message; it is literal and byte-stable like every block. Staleness, derived: a write to _tfac/memory.md is a tool call, visible in the transcript as an assistant row's tool_calls on both runtimes (the SDK mirror records assistant lines with their tool use, stream.go:186-215), so at the boundary the file is current when no assistant tool call after the last such write is outside a short read-only allowlist (file reads, searches, the view/list exec verbs) and stale otherwise — no state, no counter, the same answer from any pod. Backstop: current means the agent's file is the memory (source = agent, no wait); stale or absent means it is generated (source = generated, the memory_pending state). The asymmetry is deliberate: a false "stale" costs the person one 10–18 second wait, a false "current" ships a memory that omits work, so the allowlist stays short and a shell command always counts as work. A conversation with no assistant turn at all gets the empty row (above), no model call. The one place the would-stop nudge is worth its turn is a delegated run's completion, which it already guards; a manual conversation is never "about to finish", so there is no moment for it to fire.
Cost. One system call per boundary that finds no memory file. Requeues and takeovers are rare; step advances already have the agent's file. Budgeted on the background-jobs model with the same "no model configured → skip with a WARN, never substitute" rule the scorer uses.

Workspace by task

The one structural change. Every helper already takes the key as a role parameter (rootKey, keyID); the callers stop passing the blueprint run id and pass the task id.

Today's keying

  • Run root: worktree.RunRoot(rootKey) with rootKey = br.ID (the setups at dispatch.go:1350-1354).
  • Snapshot blob: orgID/<blueprintRunID>/workspace.tar (workspace_snapshot.go:147); lifecycle row workspace_snapshots (org_id, blueprint_run_id) (baseline:5208-5221).
  • Evictor and reaper group by blueprint run (workspace_evictor.go:142, snapshot_reaper.go:7); memory namespace is the run id (memory.go:38-52).
  • Drivability: blueprintDrivableSQL drives one conversation per run.
  • First claim of a run with no worktree_path is an unconditional fresh clone (dispatch.go:1338-1398).

Under the model

  • Key = task id for the run root, the snapshot blob, the snapshot row, the memory namespace, and the evictor/reaper grouping. A blueprint run's steps share it as before; two runs on one task now share it too; the manual conversation (§9) shares it with whatever came before or after.
  • One drivable conversation per task. blueprintDrivableSQL becomes a task-level predicate: the task's latest non-ended conversation, and for a blueprint run additionally the current step. Two agents in one tree remains impossible by construction.
  • Fresh clone only when the task has no workspace. The branch at buildStepConfig keys on the task's recorded path rather than the run's. The warm-path stat stays on conversations.worktree_path; a new conversation on an existing task is stamped with the task's path at mint, so the ladder (warm → blob → wait → fresh) finds it.
  • The branch follows the tree. A later blueprint pushes to the branch the task already has, so a pending draft PR is updated rather than duplicated. The per-run push allowance (internal/pushpolicy) is re-derived for the task's branch; base-branch policy is unchanged.
  • A failed step does not drop the tree, which makes a failed task resumable — through its next conversation, not the failed one. Today the blob is discarded twice on failure: failConversation drops the conversation-keyed one (stop.go:617) and terminateBlueprint the run-keyed one (blueprint.go:209). With the tree owned by the task, an infra failure on one step must not destroy the next attempt's starting point; both discards move to task end, under retention. Stated explicitly because it is a behaviour change rather than a consequence: the failed conversation row stays unresumable — the composer's existing rule, unchanged (MarkQueuedForResume admits open and the current step's completed, postgres/conversation.go:449-450), and its blueprint run is terminal, so nothing revives the sequencer. The task is resumable: failure is a boundary (§4), so the failed conversation is ended with its memory (the agent's file if it wrote one before dying, generated otherwise), and the next conversation — a takeover's interactive one, a re-delegation's step 0, or whoever claims it after a requeue — opens in the surviving tree with that memory injected, exactly the §5 opening. What the task looks like in between is today's shape, kept: it stays bot-claimed and in_progress with nothing running (no writer clears claimed_by_agent_id on a terminal conversation — only the user verbs do, SetClaimedByUser, TakeoverClaimFromAgent, the requeue swipes), which is deliberate: a failure needs a person's look, the lane's attention order (TFAC-954) puts it second, and an automatic return to the queue would hand a broken tree to whoever picks it next without the context of why. A crash successor is below all of this: a claim retry on the same conversation (the executor's attempt budget) ends nothing.
  • Local and multi alike. Local has a real blob store under the state root (storage.go:87-101); the evictor is disabled there by default and the restart sweep preserves parked trees. Nothing mode-specific changes.

§9

The manual conversation

A conversation a person drives on a task — the interactive type the vocabulary reserved and nothing mints today. This section defines what that conversation is once it exists, because §5, §6, §7 and §13 all depend on it: its row, its claim, its prompt, its workspace, its steady state, its end. How one is started — the route and its body, the preconditions, the Board gesture, what the task's column does — is deliberately not here; it is TFAC-378's and the Board v1's (§15).

  • Row: type = 'interactive' — the column that says what kind of conversation this is, and the one thing every reader keys on; task_id and team_id from the task; creator_user_id the person; no blueprint run, no step index, no prompt_id. The origin column is not this spec's concern: it is baseline headroom ("blueprint-step delegation vs other creation modes"), written only by its DEFAULT and read by nothing in Go, whose sole effect is the CHECK conversations_origin_requires_parents — a row with origin = 'blueprint' must carry its run, task and prompt. A manual conversation carries none, so whatever opens one writes a non-blueprint value there, and what that value is (or whether the column survives, given type already answers the question) is TFAC-378's call.
  • Claim: it runs under the task's human claim. The claim axis is XOR, so a manual conversation and a running blueprint never coexist on a task — which is what makes takeover a boundary by construction (§4) — and the claim does not move when the conversation opens, idles, or ends.
  • Drive: the same claim queue and dispatcher — the claim predicate already admits interactive (domain/agent.go:112-115); the drivability predicate is the task-level one from §7. Runtime stamped per dialect as today.
  • Prompt: a second surface in the agentprompt manifest beside machinist. The surface axis is "who am I" (spec.go:41-48: a product concept, the delegated worker), so the name is a role, not the conversation type: workbench — the agent a person works with at one task's workbench, in that task's tree, on that task's entity. Not interactive, because interactivity is not what distinguishes it: a later team-scoped agent — one that oversees a whole team, calls Triage Factory's own API routes and triggers delegations of its own — is interactive too and is a different surface again, separated on the same axis by scope (one task's tree vs the team), powers (tools in a worktree vs TF's API), and identity, with its own block files rather than a variant of these. The workbench needs its own identity, communication and memory blocks (how to talk to someone who is present, when to ask rather than assume, when to update the memory file), not the machinist's with a paragraph appended. It varies on the surface axis only, per the manifest rules, so the runtime, family and mode arms are shared. Block 1 of the system prompt is Build(spec) for that surface, shared across every workbench conversation on the same tools; block 2 is <run_context> and the tools reference. No mission and no step wrapper: the person's opening message is an ordinary first row (§5), and the opening turn is the injected prior memories and the task's <task_context> exactly as for a delegation.
  • Workspace: the task's (§7), so a later delegation continues in the same tree, and a manual conversation after a blueprint starts in the tree the blueprint left.
  • Steady state: open after each turn — a manual conversation never "completes"; it idles. The completion gate never fires, which is why R3 and §6 exist.
  • End: only at a boundary (§4) — requeue, delegate, task end; a user → user reassign is not one, the new claimant resumes it. Its memory follows §6: the file if current, generated otherwise, and the task waits while it is owed.
§10

Requeue, and the Board dialog

TFAC-952 (#1048) made requeue stop the run: finalizeRequeue now takes the same stop pass every other disposition does, under its own cause. This section is the rest of R6.

  • Stop (already lands: parks the conversation open, cancels the blueprint) → record memory (§6) → stamp the boundary (§11) → flip the task row as today → broadcast. Jira reversal unchanged. Artifacts untouched.
  • The resumability ladder gains ResumeBlockedTaskRequeued: the conversation's resumability read answers with that rung, so a message to it is refused with the reason named. Its rows are untouched — the conversation and its transcript stay readable through the reads that exist today; nothing is hidden or scrubbed.
  • Undo takes the same path (it shares the finalizer).
For the Board handoff. The requeue dialog's two-way "Keep the conversation / Clear the conversation" control and its per-branch consequence copy do not survive this model. What remains is a confirmation when a run is live ("This stops the run. Its work stays with the task."), and nothing at all otherwise — a requeue with nothing running is reversible by re-claiming. The bespoke radiogroup, the counted artifact clauses, and the "starts with nothing but the task" sentence go. Record this against TFAC-951 rather than re-deriving it in the rebuild.

Three lanes: Queued, In Progress, Done. Both middle columns go.

Claimed is a read projection — "status queued plus a claim column set" (internal/db/tasks.go:62-69) — and dragging into it is already unsupported (Board.tsx:1141-1150). With the picker as the only way to move a claim, nothing outside the Board reads it: the Overview's needs-you join names it as a status filter (one word), the Jira map and mirror never see it, the rail's queued count is unclaimed-only and stays so. The claimed value stays in the list filter vocabulary — "queued and held by someone" is a legitimate headless question — but no lane is built from it. A user-claimed task still queued sits in the Queued lane wearing its assignee mark (the lane drops only_unclaimed; the rail count keeps it) until something says "started" — what does, and whether opening a manual conversation is one of those things, is the Board's state machine, which is not this spec's (§15).

In Review was two things: for a bot-claimed task a derived approval column, flipped by recomputeTaskBoardColumn whenever the run held an unresolved artifact or parked open; for a user-claimed task a manual stage marker nothing read. Neither reached Jira — the mirror collapses both stages to InProgress on purpose (jira_mirror.go:12-17). Under this spec the derived meaning is already gone: needs-you lives on the card frame, at the head of the lane order (TFAC-954), in the rail count and on the Overview, and a queued task can hold artifacts, so the column was a third encoding of a fact the card shows. The manual meaning is the PR's or the ticket's state, not the task's. So in_review leaves the stored vocabulary: the tasks_status_check CHECK (baseline:1034) drops it, existing rows rewrite to in_progress, patchableTaskStatuses and db.TaskListStatuses drop it, the recompute and its approval-column twin are deleted, and closeTaskIfTerminalAndResolved keys on "bot-claimed by that run with nothing unresolved" rather than on a column. The Jira in_review status rule is a different axis and is untouched: an optional fourth rule on jira_project_status_rules that the settings save path already resolves and persists (InReviewMembers / InReviewCanonical, internal/server/settings.go:107, 286; the headless bootstrap too, headless.go:485), with its own migration (202608220001_jira_in_review_rule.sql) and a shipped settings UI (JiraProjectRulesGroup.tsx). What it lacks is a reader — the migration's own comment says it "feeds nothing TF polls or classifies on" and that no Jira status is read back into a TF column (TFAC-883). Removing the task status changes nothing about that rule in either direction.

Drags on the three-lane board: to Queued is requeue, to Done is complete, Queued → In Progress is the human's one stage marker. The status removal is a backend ticket with a migration in both dialects, sequenced ahead of TFAC-951; the lane deletions are TFAC-951's.

§14

Decisions

Made in the design thread; recorded so they are not re-litigated in tickets.

  • DECIDED No Clear. Context is bounded by R5, not by deletion; the "bad run" case is a human verdict on the memory; a broken tree is a workspace concern; sensitive content is a retention tool. Cleared-line semantics, message scrubbing, and snapshot discard on a gesture are all out.
  • DECIDED Requeue is a boundary; reassign is not. §4.
  • DECIDED Fork, not reuse, and in fact no fork at all. Continuation is always a new row (R5) or a resume of the same row (R4). Nothing copies messages, nothing re-parents a conversation, and the SDK needs no session fork.
  • DECIDED Blueprint steps get prior memories injected, not a file to read — as one injection:memory row per memory on both runtimes, with a link back to the source memory, rendered to the wire as one enveloped user message by the same assembler on both; the memories are compactable on both. §5.
  • DECIDED The mission lives in the system prompt on both runtimes; the task context is a user row on both. Retention by construction, no re-injection anywhere; the SDK's summarizer is trusted with the task context, which is also written to a file the mission names. §5.
  • DECIDED Artifacts carry across every boundary except task end. §8.
  • DECIDED Workspace keyed by task. §7.
  • DECIDED Three lanes. Claimed and In Review go; in_review leaves the stored status vocabulary; the bot's column recompute is deleted; the card frame and the attention order carry needs-you (§10).
  • DECIDED Resumability of completed steps is unchanged: the current step only. A boundary additionally retires that one.
  • DECIDED No cross-team reassign, for now. The reassign verb's target must be a member of the task's owning team (tasks.team_id); any other target is refused with 422 INVALID_FIELD on target_user_id. That narrows today's guard, which admits any user on a team that can see the task through task_teams (task_actions.go:290-380, "target user isn't on a team that can see this task") while never moving tasks.team_id — so under the current guard a claim can land on a user whose team RLS keeps out of the task's conversations, which is exactly the case the re-stamp question was about. Refusing removes the case rather than answering it. Moving a task between teams is a capability that does not exist today (setOwnerTeam stamps team_id at claim and nothing else writes it) and belongs with the equally unshipped transfer of entity ownership between teams; both are multi-mode concerns and neither is designed here. The one constraint this spec leaves for that work is a fact, not a prescription: conversations.team_id is frozen at insert, so a transfer cannot be a one-column update on tasks.
  • DECIDED Injection budget: the newest 5, within 32 KiB total, both constants beside the composer. Walk the task's memories newest first and mint a row for each whole memory (its agent_content; empty rows — source none — are skipped and do not count) while the running count stays at or under 5 and the running size at or under 32 KiB; stop at the first that does not fit, so the injected set is always a contiguous newest-first window and the envelope's "these are the most recent" stays true. No floor: a newest memory that alone exceeds the byte cap is not injected either, and the run falls back to what it has today — the static <entity_memory> block pointing at the folder. Why 5: the memory contract is cumulative (each memory is written with the earlier ones in context, so the newest carries the running "what is left"), the longest shipped blueprint puts two prior steps in front of its last one, and a task past five boundaries is one where the older attempts are background the agent can read on request, not handoff. Why 32 KiB: the guidance asks for 150–300 words (blocks/verbs/memory.txt), about 2 KB, so five nominal memories are ~10 KB and the cap is three times that — room for a memory that "genuinely warrants" expansion, a bound on a log dump; nothing reads memory.md with a size limit today (readAgentMemoryFile, memory.go:104-119), so this is the only guard. The selection runs once, at mint, on both runtimes — assembly wraps whatever rows exist and never re-decides.
  • DECIDED A memory's primary entity is a join row, not a column. conversation_memory.entity_id duplicated the primary role in conversation_memory_entities, the table that already fans one memory out to every entity a conversation produced or touched; the column goes, and the this-task split is a join on the conversation's task_id rather than a second denormalized column. This is what lets a taskless conversation write memory with no primary at all and still be found from the PR it opened (§11).
  • DECIDED Generation that cannot happen keeps the task waiting; there is no waiver. Three answers for three cases (§6): a conversation that never reached an assistant turn gets the empty row mechanically, no model call; a transient provider fault is the provisioner's to outlast through the systemllm breaker, with the attempt row naming it; a persistent one is a configuration error the org fixes, surfaced per task now and durably once TFAC-878 lands. The block itself only ever holds the two verbs that need a model.
  • DECIDED Where the generated memory runs for a step the reactor ends. The control plane, off the same derived state everything else reads: the reactor ends the step and writes nothing but the boundary (ended_at, ended_reason); the conversation is then owing by the §6 predicate (ended, no memory row), and a control-plane job — the scorer's shape, on the system-jobs path with the org's credential — fulfils it. The executor holds no model credential in multi, so it could never have generated it; the derived state is what the brain's provisioner sweeps, and the reactor rings the memory_owed doorbell over tf_ctl to shorten the wait — the cred_request pattern, doorbell plus backstop sweep (§6). Local is the same code at N=1.
§15

Out of scope

Named so the backend tickets cut from this spec do not absorb them.

  • The run station redesign. Showing a task's conversations as one scroll, the boundary markers, the closed-composer rendering beyond the existing rung mechanism — all of it is blocked on this spec and none of it is in it. This spec ships the data (order, ended_at/ended_reason, the task-keyed reads) and leaves the surface as it is. One requirement is recorded here for that redesign so it is not lost, because it follows from §6 rather than from any design pass: each ended conversation renders its memory in a slot above the boundary separator that closes it — the agent's own file or the generated one, provenance shown — and while the task is memory_pending that slot is a skeleton, so the person disabled from sending can see where the summary they are waiting on will appear and that the wait is for it. The data for both states is already in this spec: the slot is filled by the conversation_memory row, and the skeleton is the derived state the composer reads.
  • Starting a manual conversation. The route and its body, its preconditions (who may open one, what a live conversation on the task means for it), the Board gesture that leads to it, and whether opening one moves the task's column — none of it is here. It is TFAC-378's (user-triggered interactive runs) together with the Board v1 (TFAC-951), and it waits on that UI. What this spec fixes for that work so it does not have to re-decide: the row it writes (§9), the workspace it starts in (§7), the memories it opens with (§5), and the one invariant any opener holds — it refuses while the task is memory_pending (§6).
  • An entity-history view. Same data, later.
  • Retention and scrubbing. No delete, archive, or scrub route; the snapshot reaper is the only retention today, and an admin tool for transcripts is its own decision.
  • A workspace reset verb. A broken tree is reset by the agent or by a later affordance; nothing here discards a task's workspace on a gesture.
  • SDK session forking. Not needed: no conversation is ever forked (§14).
  • Undoing external mutations. PRs, comments, and branches an agent produced are real objects with their own lifecycle; the existing teardown at task end is the only retraction.

Risks

  • RISK Re-keying the workspace touches the evictor, the reaper, and the claim gate at once. Mitigation: phase B is its own PR with the conformance suites for all three, and the key stays a role parameter so no helper changes signature.
  • RISK A generated memory is worse than the agent's. Mitigation: provenance column; the agent's own overwrites it on a later conclusion; the human verdict channel remains.
