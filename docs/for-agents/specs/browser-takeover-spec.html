01What takeover is today

Not a wipe — a one-way door.

The mental model of "takeover destroys the run" is a version behind. Today's takeover already preserves and resumes: it moves the worktree somewhere durable, copies the Claude session so claude --resume attaches, and hands you a command. The real gap is narrower and sharper — there's no way back in.

✓

It already preserves the work

The worktree is moved to ~/.triagefactory/takeovers/, not deleted; the session JSONL is copied and re-encoded so --resume finds it; the run lands in a terminal taken_over status with a held-takeovers banner and a triagefactory resume shortcut. Startup cleanup even fails safe.

⥂

But it's an exit, not a cockpit

taken_over is terminal. Once you eject, you live in your terminal forever — there is no transition back into Triage Factory. You lose the board, the live stream, the team context. That's the part users feel, and the part this redesign kills.

⚠

The destructive path is a different button

The "wipes everything" behavior is Cancel (SIGKILL + worktree delete), not Takeover. Three operations exist today — Cancel (abandon), Takeover (eject + preserve), Release (tear down a held takeover) — and none let a human steer in place.

02The question we set out to decide

The fork wasn't real.

We framed it as two architectures: A, pause-and-respawn (re-run --resume per message), versus B, a long-lived process you talk to. The Agent SDK that Triage Factory already embeds (wrapper.mjs, pinned claude-agent-sdk@0.2.137) collapses the choice.

the catch

pause needs the live plane

// only in streaming-input mode:
query.interrupt() · streamInput() · setPermissionMode()
// wrapper.mjs:86 passes a plain string → none of these
  • interrupt() — the basis of user-initiated pause — exists only in streaming-input mode.
  • Today the wrapper hands the SDK a string prompt, so TF has no interrupt — only SIGKILL.
  • So even "Model A with pause" needs the streaming bridge. There is no cheap pause.
the payoff

the bridge is the whole plane

// once prompt is an AsyncIterable you also get:
streamInput · interrupt · canUseTool · getContextUsage · readFile · rewindFiles
  • The moment you switch modes for pause, you also get send-message, permissions, context metering, even file-rewind.
  • The SDK ships a readFile() documented "for the remote sidebar viewer" — browser steering is a first-class use case.
  • And live steering is cheaper per message than respawn — see next.

A vs B was a false choice. Live is the path; resume is the safety net.

03Measured, not assumed

Every assertion passed.

Run against the exact SDK build TF ships, authenticating the same way wrapper.mjs does — local Claude login, no API key. Total spend across the whole spike ≈ $0.08. Scripts and a full write-up live on aa/takeover-spike.

✓

Interrupt is instant and clean

interrupt() resolved in 8ms, stopping the agent after 1 of 10 files — no SIGKILL, no torn state.

✓

You can steer the live process

After interrupt, streamInput() delivered a new instruction into the same process and the agent obeyed — input=10, cache_read=13469, zero replay.

✓

Resume recovers everything, cold

A fresh process (resume: sessionId, same cwd) recalled the task, the interrupt point, and the steering message verbatim — same session id. The "resume later / crash / restart" story holds.

✓

Permissions round-trip to the browser

canUseTool fired with tool + input; an async deny was honored as an error result. A risky rm -f was gated; a trivial echo auto-passed — so the UI only prompts for consequential actions.

$

Cheap inside a burst — and the cache is server-side

While a run is actively churning, each turn pays only the delta (~18 input tokens; history served as cache_read) ≈ $0.0045/turn, no respawn. But the prompt cache lives on Anthropic's clock — a warm-but-idle process doesn't hold it open. Telemetry shows mixed TTLs: the stable prefix (~13K tokens) in a 1-hour cache, the growing tail in the 5-minute default. So past ~5 min idle, warm and resume pay the same tail rebuild — staying warm then buys latency, not tokens.

⚠

Two shapes the Go side must learn

An interrupt surfaces as a result with subtype: error_during_execution (must not be read as failure), and a streaming process emits N init+result envelopes — run.go returns on the first today.

04One plane, two layers

A warm process. A cool backstop.

There's no "steered" run — just a run. Every one executes as a long-lived streaming process, so any of them can take a message or be interrupted at any moment, and any of them can run fully autonomously and never get one. The split isn't human-vs-bot — it's working vs idle: warm while the agent is doing work, hibernated to a durable resume the moment it goes quiet.

warm · the live run

live process · the hot path

  • wrapper.mjs becomes a bidirectional bridge: AsyncIterable prompt; stdin carries a control protocol (user_message · interrupt · permission_response · set_mode); stdout streams the envelopes TF already parses.
  • canUseTool emits a permission request on stdout and awaits the browser's answer on stdin.
  • Every run runs this way — autonomous or attended; a message may arrive, or never. No per-message replay inside a burst; interrupt in milliseconds.
cool · the machine remembers

resume-by-session · the backstop

  • Already proven: resume: sessionId reloads the full transcript from the on-disk JSONL.
  • Covers crash, server restart, and idle hibernation — when the agent goes quiet (yielded, or just not working), close the process and free the slot; respawn from session_id + worktree on the next trigger, human or system.
  • This is "Model A's" mechanism — demoted from per-message hot path to the recovery + capacity layer. Same path whether a human message or an autonomous continuation wakes the run.
What today's architecture can't do yet — the real work
  • dispatcherThe single inline run dispatcher executes steps synchronously — a process parked between turns would freeze the queue. Runs must execute off-dispatcher (the yield/resume goroutine already does) but stay alive while working (yield exits the process today).
  • registryThe spawner tracks only runID → CancelFunc. The live path needs runID → { process, stdin, interrupt } surviving across HTTP turns.
  • parserstream.go must loop over N envelopes and label interrupts explicitly — the bridge called interrupt, so it never has to guess from error_during_execution.
  • multiMulti-mode needs a persistent bidirectional channel into the per-org gVisor sandbox. The browser↔TF websocket hop is identical to local — only the process's location differs. Horizontal scale (N pods) is a further step, deferred — see below.
05The point of doing this now

Local is multi, at N=1.

The reason to scope this before multi-mode hardens: browser steering is one control surface for both modes. The browser talks to TF over the websocket it already has; TF talks to the process. Only where the process runs changes.

And the same split scales out — TFAC-71, deferred

Past one executor, a live run is a sticky, host-bound resource — it pins to one pod, exactly like a curator session. The warm/cool split is the placement model: the warm process homes to an executor (sharded by org,repo), and the cool resume layer — built on the portable workspace snapshot (TFAC-23) — is what lets it re-home on any pod. Control ops (message / interrupt / resume) join the planned conversion of cancel·takeover·resume from the in-memory s.cancels map to DB-signaled operations to the owning executor; output fans out via Postgres LISTEN/NOTIFY so any pod serves any browser. Hibernation un-pins the run and reclaims one of the ≈256 sandbox slots per host — the drain/rebalance primitive, for free.

Not a launch blocker — single-executor multi-mode ships first. The only thing it asks of this build: route control through a thin indirection that's in-process today and DB-signaled later, and record run→executor ownership even at N=1 — so scale-out is a step, not a rewrite.

06The path forward

Bridge first. Eject last.

Six phases, local before multi. Browser permissions are in the first cut. Eject-to-terminal is removed entirely — once you can steer in the browser, the terminal escape hatch and its machinery (held-takeovers, Release, triagefactory resume) go away. Tap a card for the gist.
